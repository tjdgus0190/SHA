# Luminance Overlay App

`tourbox-luminance-picker`(Photoshop UXP 플러그인)와 짝을 이루는 독립
데스크톱 앱. **브러시로 그리는 중 Ctrl을 누르고 있으면 펜촉(커서) 위치에
클릭 가능한 컬러 팝업이 뜨고, 타일을 클릭하면 즉시 Photoshop 전경색으로
적용됩니다.**

## v8.8 변경사항 — 와콤 펜 검정 전환 근본 원인 수정 + 사용성 개선

### 검정 전환: 찾은 근본 원인 2가지
1. **COM 읽기 null → 검정** (`com-bridge.js`): Photoshop이 펜 입력 처리로
   바쁠 때 `$app.ForegroundColor.RGB`가 예외 없이 `$null`을 주면
   `[int]$null = 0`이라 그대로 `COLOR 0,0,0`이 보고됐다. 이제
   `Read-ForegroundColor`가 중간 객체/채널이 하나라도 `$null`이면 "읽기
   실패"로 버리고, 검정은 `HexValue == "000000"` 교차 확인 + 5회 연속(약
   0.5초) 안정돼야만 보고한다.
2. **UXP `grain` 키** (`uxp-plugin/index.js`): Photoshop 디스크립터의
   초록 채널 키는 `green`이 아니라 `grain`이라 스포이드 `set` 이벤트의 직접
   추출이 항상 실패하고, 매번 "재조회"(=펜 중 검정을 읽는 경로)로
   빠지고 있었다. 또 500ms 폴링이 읽은 값을 검증 없이 오버레이로 보냈다.
   → `grain`/HSB/Lab/Gray/CMYK 디스크립터 지원, 폴링은 "3회 연속 동일 +
   검정 제외" 안전망으로 축소, D(`reset`)/X(`exchange`) 이벤트 직접 처리.

### 추가 방어 (`main.js`)
- **0차 방어(검정 보류 700ms)**: 신뢰 못 하는 경로의 검정은 0.7초 보류,
  그 사이 다른 색이 오면 화면/히스토리에 한 번도 안 나타나고 폐기.
- 왕복 글리치(색X→검정→색X)는 **첫 회부터** 히스토리에서 제거.
- UXP 연결 중엔 COM 전경색 폴링 자체를 정지(`POLL OFF`) — Photoshop 부하 감소.

### 사용성
- 색 적용: UXP v2 플러그인이 연결돼 있으면 UXP로만 SET하고 실패/1.5초
  무응답 시에만 COM 재시도(예전엔 항상 이중 SET → 혼잡/실패 원인).
- 배경색 변경(Alt+스포이드)이 전경색으로 오인되던 버그 수정.
- 팝업에 닫기(×) 버튼 추가(Esc가 안 먹는 환경 대비).
- 팝업이 열린 상태에서 고른 색이 히스토리 줄에 즉시 반영.
- 히스토리 중복 제거(같은 색은 맨 앞으로) + **앱 재시작 후에도 유지**
  (`%APPDATA%\luminance-overlay-app\sha-paint-history.json`).
- 로그 파일 5MB 회전, 150ms마다 쌓이던 "Photoshop 비활성" 로그와 클릭마다
  찍히던 마우스 로그 제거. UXP 플러그인 로그가 이제 앱 로그에 `[uxp]`로 남음.

### 배포 주의
- **UXP 플러그인도 반드시 같이 교체**(manifest 1.1.0). 구버전 플러그인이면
  예전 이중 SET 방식으로 동작하고 grain 수정이 적용되지 않는다.
- 번들 `.ccx`(`resources/tourbox-luminance-picker.ccx`)는 재패키징 필요.

**검증**: `verify.js`, `test-black-glitch.js`(9개 시나리오),
`test-uxp-plugin.js`(모의 Photoshop 11개), `test-com-bridge-ps.js`(실제
PowerShell로 PS_SCRIPT 실행, 모의 COM 객체 7케이스 + TCP 프로토콜) 전부 통과.
**실제 와콤 펜 + Photoshop 실기 검증은 아직 안 됨.**

## v8.7 변경사항 — 자동 트리거/숨김 기능 전체 정리

### 확정된 결론

UXP 패널은 Photoshop이라는 하나의 창 안에 항상 속한 "영역"일 뿐,
독립된 OS 창이 아니라는 게 실측으로 확정됐습니다(`EnumWindows`로
전체 창 목록을 덤프해도 "Luminance Picker"가 아예 없었음, 드래그해도
Photoshop 창 밖으로 절대 안 나감). 이 구조상 외부(SHA Paint)에서
그 패널을 열거나 숨기는 건 원천적으로 불가능합니다.

### 정리한 것

- **`com-bridge.js`**: `Invoke-TriggerUxpCommand`, `Hide-WindowByTitleSubstring`,
  Win32 타입 정의, `TRIGGER_UXP` 디스패치, 메인 루프의 지속 감시 로직,
  Node 쪽 `triggerUxpCommand` 함수/export 전부 제거
- **`mac-bridge.js`**: 대응하는 `triggerUxpCommand` 제거
- **`main.js`**: Photoshop 감지 시 자동 트리거 호출, "재연결" IPC
  핸들러 제거. 상태 패널 높이도 행 개수(5→4)에 맞춰 재조정
- **상태 패널 UI**(`status-panel.html/js`, `status-preload.js`):
  "재연결" 버튼과 관련 로직 전부 제거
- **UXP 플러그인**(`manifest.json`, `index.js`): 명령(command)
  엔트리포인트 전부 제거(패널만 남김), 패널 크기도 원래의 실사용
  가능한 크기(300×420)로 복원(더 이상 숨기지 않으므로 극단적으로
  작게 만들 필요 없음)

### 최종 사용 방법

패널을 **수동으로 한 번 열어서** 화면 구석에 도킹 후 접어두면 됩니다.
도킹 위치는 Photoshop을 재시작해도 기억되는 게 확인됐습니다. 이
상태로 연결되면 검정 오독 문제는 이미 확실하게 해결된 상태(UXP 연결
시 COM 폴링 자동 비활성화)를 유지합니다.

**검증**: 모든 수정 파일을 `node --check` + 실제 `require()`까지
재현해서 문법/런타임 에러가 없는 것, 잔여 참조가 전혀 없는 것을
확인했습니다. jsdom으로 상태 패널 UI가 재연결 버튼 제거 후에도
크래시 없이 정상 로드/렌더링되는 것도 확인했습니다.

## v8.6 변경사항 — 창을 못 찾을 때 진단용으로 모든 창 제목을 덤프

패널을 최소화한(접힌) 상태에서도 숨김이 안 되는 상황을 보고받았습니다.
화면에 보이는 "Luminance Picker"라는 텍스트가, 실제 OS 차원의 창
제목과 다를 수 있습니다(도킹된 패널은 애초에 별도 창이 아닐 수도
있음) — 그래서 추측 대신 직접 확인할 수 있게 했습니다.

**추가한 것**: `Hide-WindowByTitleSubstring`이 타겟 창을 못 찾으면,
5초에 한 번씩(로그 폭증 방지) **그 순간 보이는 모든 창의 실제 제목을
전부 로그로 남깁니다.** 이걸 보면 "Luminance Picker"에 해당하는 실제
창이 있긴 한지, 있다면 진짜 제목이 뭔지 바로 확인할 수 있습니다.

**검증**: `require()`까지 재현해서 런타임 에러 없음을 재확인했고,
스크립트 전체의 `${...}` 패턴을 다시 전수 조사했습니다.

**확인 부탁드립니다**: 최소화된 상태에서 로그를 다시 보내주시면,
`[com-bridge-debug] 'Luminance Picker' 못 찾음. 현재 보이는 창 제목
전체: ...` 줄을 보고 정확한 다음 수를 정하겠습니다.

## v8.5.1 긴급 수정 — 시작조차 안 되던 치명적 버그

v8.5에서 추가한 로그 한 줄에서 `${hiddenNow}`(PowerShell 변수 보간
의도)를 썼는데, 이 PowerShell 스크립트 전체가 **JS 템플릿 리터럴
(백틱 문자열) 안에 들어있다는 걸 놓쳐서**, JS가 이걸 먼저 자기
템플릿 리터럴 보간(`${표현식}`)으로 해석해버렸습니다. `hiddenNow`라는
JS 변수는 존재하지 않으니 `com-bridge.js`를 불러오는 순간(앱 시작
직후) 바로 `ReferenceError`가 나서 **앱 자체가 뜨지도 못했습니다.**

PowerShell 전용 보간 문법(`$($hiddenNow)`, 중괄호 없이 — 이미 파일
다른 곳에서 쓰이던 안전한 패턴)으로 고쳤습니다.

**검증**: 이번엔 `node --check`(문법 검사)뿐 아니라 실제로
`require("./com-bridge.js")`를 실행해서 템플릿 리터럴이 평가되는
순간까지 재현해 에러가 없는지 확인했습니다. 그리고 스크립트 전체에서
`${...}` 패턴을 전수 조사해서, 남아있는 2개(`TCP_PORT`,
`LOOP_INTERVAL_MS`)가 전부 실제 JS 스코프에 존재하는 의도된 보간인지
하나씩 확인했습니다. 죄송합니다 — 이런 실수는 빌드 전에 항상
require 테스트까지 하겠습니다.

## v8.5 변경사항 — "여는 것"과 "숨기는 것"을 분리: 수동으로 열어도 자동으로 사라짐

### 상황: 이 환경에서 자동 단축키 트리거는 완전히 막혀있음을 확인

명령(1개, 2개 둘 다), 패널 — 어떤 방식으로 해도 Photoshop의 Keyboard
Shortcuts 편집기에서 "플러그인" 카테고리 자체가 펼쳐지지도, 단축키가
지정되지도 않는 게 스크린샷으로 재확인됐습니다. 이건 이 환경의
Photoshop이 서드파티 플러그인 메뉴 항목을 다루는 데 근본적인 문제가
있는 것으로 보이고, 더 파고들어도 뚫릴 가능성이 낮다고 판단했습니다.

### 발상 전환: "자동으로 여는 것"과 "열리면 숨기는 것"을 분리

자동으로 여는 쪽(단축키)은 막혔지만, **"열리면 즉시 숨기는" 쪽은
저희가 완전히 통제할 수 있습니다.** 사용자가 Plugins 메뉴에서 딱 한
번 수동으로 패널을 클릭해서 열어도, SHA Paint가 백그라운드에서
**100ms마다 계속 감시**하고 있다가 "Luminance Picker" 창이 뜨는 걸
발견하면 Win32 `ShowWindow(SW_HIDE)`로 **즉시(거의 눈에 안 띌 정도로
빠르게) 숨겨버립니다.**

이전엔 이 숨김 로직이 "자동 트리거 직후 한 번만" 실행됐는데, 이제는
메인 폴링 루프 안에 넣어서 **항상 감시 중인 상태**로 바꿨습니다 —
사용자가 언제 어떻게 패널을 열든(수동 클릭이든 뭐든) 상관없이 뜨는
순간 바로 잡아서 숨깁니다.

**여전히 남는 제약**: 도킹되지 않고 **떠 있는(floating) 상태**여야
별도 창으로 잡혀서 숨겨집니다. 이전에 도킹해두셨다면 도킹을 풀어야
합니다.

## v8.4 변경사항 — "작게"가 아니라 "완전히 안 보이게": Win32로 창 자체를 숨김

### 지적 반영: 크기 축소가 아니라 진짜 숨김이 맞다

"패널을 작게 만드는 게 아니라 아예 안 보여야 한다"는 지적을 받고
재설계했습니다. 명령(command) 메뉴 항목이 Photoshop의 Keyboard
Shortcuts 편집기에서 트리 구조가 깨져서 단축키 지정 자체가 막혀
있었던 문제(다른 카테고리처럼 들여쓰기가 안 되는 렌더링 버그로 추정)
때문에, 명령 대신 **패널 자체**에 단축키를 지정하는 방식으로
전환했습니다. 패널을 여는 것까진 필요하지만, 그 직후 **Win32 API로
그 창 자체를 OS 차원에서 완전히 숨깁니다.**

### 구현: EnumWindows + ShowWindow(SW_HIDE)

`Invoke-TriggerUxpCommand`가 단축키를 보내 패널을 연 뒤, 0.6초
기다렸다가 `EnumWindows`로 열려있는 모든 창을 순회하면서 제목에
"Luminance Picker"가 포함된 창을 찾아 `ShowWindow(SW_HIDE)`로 완전히
숨깁니다. 이건 창을 파괴하거나 최소화하는 게 아니라 "보이지 않게"만
만드는 것이라, 내부 JS 실행과 WS 연결은 계속 살아있습니다.

**중요한 제약**: 이 방식은 패널이 **떠 있는(floating) 상태**일 때만
확실히 작동합니다. 도킹된 패널은 Photoshop 메인 창의 일부라 별도
창으로 안 잡힐 수 있습니다 — 만약 이전에 패널을 도킹해두셨다면,
**도킹을 풀어서(드래그해서 분리) 떠 있는 상태로 만들어주셔야** 이
숨김 기능이 작동합니다.

**확인 방법**: 로그에 `패널 창 N개 숨김`이 찍히면 성공, `숨길 창은
못 찾음(도킹된 패널일 수 있음)`이 찍히면 도킹을 풀어야 합니다.

## v8.3 변경사항 — 중복 실행 원천 차단 (UXP Developer Tool 없이도 진단)

### 상황: UXP 콘솔을 확인할 수 없는 환경에서 "연결은 되는데 로그엔 안 남는" 미스터리

"수동으로 패널을 열면 제대로 작동하는데 SHA Paint 로그엔 UXP 연결
기록이 안 남는다"는 보고를 받았습니다. UXP Developer Tool 콘솔을

### 가장 유력한 원인: SHA Paint 중복 실행

예전부터 있었던 "프로세스가 안 꺼진다"는 문제와 연결지어보면: 만약
이전 SHA Paint 인스턴스가 완전히 안 꺼진 채로 새로 하나를 더
실행하면, **새 인스턴스는 TCP(51900)/WS(51837) 포트를 잡으려다
조용히 실패**하면서도 창은 멀쩡히 뜹니다. UXP는 먼저 떠 있던
(예전) 인스턴스에 연결되니 "겉보기엔 작동"하는데, 지금 보고 있는
로그 파일(새로 켠 인스턴스 것)에는 그 연결 기록이 전혀 안 남는
—정확히 보고받은 증상과 일치하는 시나리오입니다.

### 수정: 애초에 중복 실행 자체를 차단

`app.requestSingleInstanceLock()`으로 SHA Paint가 이미 실행 중이면
새로 실행되는 인스턴스가 **즉시 자기 자신을 종료**하도록 했습니다.
`app.quit()`가 비동기라는 점을 감안해, `app.whenReady()` 블록 자체를
잠금 성공 시에만 실행되도록 이중으로 방어했습니다. 추가로, 혹시
모를 다른 원인으로 포트 충돌이 나면(EADDRINUSE) 이제 "다른 SHA
Paint 인스턴스가 실행 중일 수 있습니다"라는 명확한 메시지가 로그에
남습니다.

**검증**: 잠금 획득 성공/실패 각각의 경우에 `app.whenReady()`(COM
브릿지, WS 서버 시작 등 포함)가 정확히 실행/차단되는 것을 순수
로직으로 확인했습니다.

**확인 부탁드립니다**: 이 빌드로 교체하신 뒤, 작업 관리자에서 기존
SHA Paint(및 관련 PowerShell) 프로세스를 전부 완전히 종료하고 딱 한
번만 실행해주세요. 그 상태로 다시 테스트했을 때 로그에
`[overlay] UXP plugin connected`가 찍히는지 확인 부탁드립니다.

## v8.1 변경사항 — 연결 해제 로그 추가 (패널을 꺼도 연결이 유지되는지 직접 확인 가능하게)

## v8.0 변경사항 — 결정적 발견: COM 폴링과 UXP가 동시에 경쟁하고 있었음

### 스크린샷+로그로 확인된 정확한 원인

"플러그인 패널로 연 화면은 검은색 전환이 안 되는데 SHA Paint 팝업만
그래" — 이 한 문장으로 정확한 원인이 드러났습니다. **UXP가 연결돼
있어도, COM 브릿지(TCP) 폴링은 멈추지 않고 계속 별도로 돌고
있었습니다.** UXP 쪽(이벤트 직접 구독, 신뢰도 높음)은 깨끗한 상태를
유지하는데, COM 폴링 쪽(예전부터 문제였던 경로)이 여전히 같은 팝업
상태를 두고 경쟁하며 검정을 흘려보내고 있었던 것입니다. UXP 패널
자체는 COM 폴링과 완전히 무관한 별도 표시라 전혀 영향을 안 받았던
것이고요.

### 수정: UXP 연결 시 COM 폴링 완전 무시

`uxpSocket`이 연결돼 있는 동안은, COM 폴링에서 오는 색 보고를 아예
반영하지 않도록 게이트를 추가했습니다. UXP 연결이 끊기면(패널을
닫는 등) 다시 COM 폴링이 안전하게 폴백으로 작동합니다.

**검증**: UXP 미연결 시 COM 폴링이 정상 반영되는 것(폴백 역할),
연결 시 검정을 포함한 모든 COM 폴링 결과가 완전히 무시되는 것,
연결이 다시 끊기면 폴백이 재개되는 것을 순수 로직으로 확인했습니다.

### "플러그인을 안 열어도 되게" — 확인 필요 사항

`connectOverlayApp()`/이벤트 리스너 등록 코드는 패널 표시 핸들러
밖(모듈 최상위)에 있어서, 패널이 로드되기만 하면 표시 여부와
무관하게 작동할 가능성이 있습니다. 다만 UXP 플러그인이 Photoshop
실행 시 자동 로드되는지, 아니면 사용자가 패널을 최소 한 번 열어야
로드되는지는 이 환경에서 검증이 불가능합니다. 가장 현실적인 방법은
**패널을 한 번 도킹해두고 그 상태로 Photoshop을 종료 → 재실행 시
자동으로 다시 뜨는지 확인**하는 것입니다 — Photoshop은 보통 도킹된
패널 배치를 기억하는 경향이 있어서, 이렇게 하면 이후로는 매번 수동
실행 없이 백그라운드에서 작동할 가능성이 높습니다.

로그에 반복된 메시지: **"이 버전의 Photoshop에서는 이 기능을 사용할 수

다시 테스트가 필요합니다.

## v7.8 변경사항 — 구조를 바꿈: UXP 이벤트 직접 구독으로 근본 해결 시도

### 결정적 단서: "마우스는 정상, 와콤만 검정"

이 한 문장이 지금까지의 전제(단순히 "Photoshop이 바쁘면 오독한다")를
다시 보게 만들었습니다. 마우스 클릭 브러시질도 Photoshop을 똑같이
바쁘게 만드는데 검정이 안 뜬다면, 문제는 "바쁨" 자체가 아니라
**와콤 특유의 고빈도 압력/기울기 입력 스트림이 마우스보다 훨씬 심하게
Photoshop 메인 스레드를 몰아붙이는 것**으로 보입니다. 그 정도로
몰아붙여지면, 외부에서 무엇을 물어보든(COM이든, UXP 폴링이든) 그
순간엔 다 신뢰할 수 없는 상태가 됩니다 — 실제로 UXP 플러그인 자체도
`app.foregroundColor`를 500ms마다 폴링하고 있었는데, **이것도 COM과
똑같이 취약한 구조**였습니다.

### 구조 변경: 폴링을 버리고 Photoshop의 이벤트를 직접 구독

`action.addNotificationListener(["set"], ...)`로 Photoshop 내부의
"set" 액션 이벤트를 직접 구독하도록 UXP 플러그인(`index.js`)을
바꿨습니다. 이건 "지금 색이 뭔지 물어보는" 폴링이 아니라, Photoshop이
"방금 이렇게 바뀌었다"고 알려주는 이벤트입니다.

**핵심 개선**: 이전에도 이 리스너를 등록한 적이 있었지만, 이벤트가
오면 여전히 `app.foregroundColor`를 **재조회**했습니다 — 이벤트를
"신호"로만 쓰고 값은 다시 물어봤던 겁니다. 이번엔 **이벤트의
디스크립터 자체에 담긴 값**(우리가 SET할 때 넣었던 것과 같은 `to`
필드)을 직접 꺼내 씁니다. 이건 "그 순간 다시 물어본 값"이 아니라
"실제로 그 액션이 설정한 값"이라, 애초에 재조회 특유의 타이밍 문제가
발생할 지점이 없습니다.

디스크립터 구조를 100% 확신할 수 없어서(이전 시도에서 구조 추측이
틀려 팔레트가 전혀 안 움직이는 문제가 있었다는 기록이 코드 주석에
남아있었음), 여러 후보 경로를 다 시도하고, 실패하면 예전처럼 재조회로
안전하게 폴백합니다 — 이 개선이 안 먹혀도 최소한 지금까지의 동작보다
나빠지진 않습니다.

### 신뢰 플래그로 방어 로직과의 충돌 방지

이벤트에서 직접 뽑은 값은 재조회가 아니라서 오독일 수가 없습니다.
그런데 기존에 쌓아온 검정 방어 로직(왕복 감지 등)을 그대로 거치게
하면, 예전 세션에서 다른 색 조합이 글리치로 확정돼 있었다는 이유로
**이 정확한 값이 억제될 위험**이 있었습니다. 그래서 `trusted` 플래그를
추가해서, 직접 추출에 성공한 값은 방어 로직을 완전히 건너뛰고
바로 반영하도록 했습니다. 재조회 폴백 경로로 온 값은 여전히 기존
방어 파이프라인을 거칩니다.

WS로 들어온 색이 히스토리에 안 남던 부수적인 문제(`applyIncomingColor`
파이프라인을 안 타서 `pushHistory`가 안 불렸음)도 이번에 함께
바로잡았습니다.

**검증**: `extractRgbFromSetDescriptor`가 여러 구조 후보(정상,
대문자 변형, 검정값, 구조 불일치, 범위 밖 오염값)에서 정확히
동작/실패하는 것을 순수 로직으로 확인했습니다. `trusted` 플래그에
따라 방어 로직을 우회하거나 통과시키는 분기도 검증했습니다.

**적용 방법**: 이번엔 Electron 앱뿐 아니라 **UXP 플러그인
(Photoshop 쪽 패널)도 다시 설치**해야 합니다. 트레이 메뉴의
"Photoshop 플러그인 설치..."로 새 `.ccx`를 다시 설치해주세요.

**솔직히 말씀드리면**: 이것도 실기 검증 전입니다. 다만 지금까지와
달리 "폴링을 버리고 이벤트를 직접 구독"한다는 점에서 구조 자체가
다르고, "마우스 vs 와콤" 단서와도 정확히 맞아떨어지는 방향이라
기대를 걸어볼 만하다고 생각합니다. 디스크립터 구조가 예상과 다르면
진단 로그(`set 이벤트... 원본 디스크립터`)가 남으니, 그걸 보내주시면
정확히 맞춰서 고칠 수 있습니다.

## v7.7 변경사항 — 근본 원인에 더 가까운 새 시도: 읽기도 SET과 같은 경로로

### 그동안 못 써본 카드: "왜 SET은 안정적인데 읽기는 불안정한가"

SET(`Invoke-SetColor`)은 수백 번의 로그에서 `SET_OK`로 안정적으로
성공해왔습니다. 원리를 보면: Photoshop이 바쁘면 **예외를 던지고**,
우리가 그 예외를 잡아서 재시도합니다. 반면 지금까지 쓰던 읽기
(`$app.ForegroundColor.RGB`)는 단순 프로퍼티 접근이라, 바빠도
예외 없이 조용히 틀린 값(전부 0)을 돌려주는 것으로 보입니다 — 그래서
"이게 오독인지 진짜인지" 사후에 추측해야만 했던 것입니다.

### 새 시도: 읽기도 Action Manager(`ExecuteActionGet`)로

`ExecuteAction`(SET이 쓰는 것)의 읽기 버전인 `ExecuteActionGet`으로
전경색을 읽도록 바꿨습니다 — 같은 액션 엔진을 통과하므로, SET처럼
바쁠 때 예외를 던질 가능성이 높습니다. 예외가 나면 SET과 똑같이
80ms 간격으로 최대 5번 재시도하고, 그래도 안 되면 **틀린 값을
보고하는 대신 이번 폴링 자체를 건너뜁니다**(`$null` 반환) — 이게
지금까지의 모든 시도와 근본적으로 다른 지점입니다. 지금까지는
"일단 값을 받고 나서 그게 맞는지 사후에 판단"했다면, 이제는 "애초에
믿을 수 없는 값은 받지도 않는" 방식입니다.

혹시 이 API 구조가 이 Photoshop 버전과 안 맞을 가능성도 배제할 수
없어서, 5번 재시도까지 실패하면 **예전 방식(단순 프로퍼티 읽기)으로
안전하게 폴백**합니다 — 최악의 경우에도 지금까지의 동작보다 나빠지진
않습니다.

기존에 쌓아온 방어층(왕복 감지+세션 학습, SET 그레이스)은 안전망으로
그대로 뒀습니다 — 이번 시도가 완벽하지 않더라도 여전히 도움이 됩니다.

**진단 로그 추가**: 이 새 방식이 처음 성공하면 로그에 남고, 재시도
끝에 성공하면("바쁜 상태를 실제로 감지하고 있다는 증거") 그것도
남습니다. 5번 다 실패해서 예전 방식으로 폴백하면 그 사실과 마지막
에러 메시지도 남습니다.

**솔직히 말씀드리면**: 이건 실기에서 검증 못 한 새로운 시도입니다.
`ExecuteActionGet`이 COM에서 정확히 이 방식대로 동작하는지, 중첩된
`GetObjectValue`/`GetDouble` 구조가 이 코드가 가정한 그대로인지는
실제로 돌려봐야 확실해집니다. 다만 SET에서 이미 검증된 것과 똑같은
메커니즘을 재사용한 거라, 지금까지의 순수 추측 기반 시도들보다는
근본 원인에 더 가깝게 다가간 시도라고 생각합니다.

**확인 부탁드립니다**: 검정이 재현되면 로그에서 `Action Manager 읽기
최초 성공`, `재시도 끝에 성공함`, `5회 재시도 모두 실패` 중 어떤 게
찍히는지 봐주세요 — 이걸로 이 새 방식이 실제로 문제를 잡아내고
있는지 바로 확인할 수 있습니다.

SET 이후 경과 시간을 역산한 결과: `4104ms`(그레이스 4초를 **104ms

### 세션 단위 학습 추가

"이번 세션에서 이미 한 번이라도 왕복 글리치가 확정된 적 있다"는 건
지금 이 PC/Photoshop 조합 자체가 글리치가 잦은 상태에 있다는 강한
증거입니다. 그렇다면 그 이후에 나오는 **새로운 색 조합**의 검정도
굳이 왕복 2회를 다시 기다릴 필요 없이, **1회만 보고도 즉시 학습해서
억제**하도록 했습니다(확정 후 5분간 임계값을 1로 완화).

**검증**: 색A로 첫 학습(왕복 2회 필요, 최초 1개는 불가피하게 남음)한
뒤, 완전히 다른 색B로 새 스트로크를 시작했을 때 **단 1회 왕복만에
즉시 확정되고 소급 제거되는 것**을 확인했습니다 — 이전 같으면 색이
바뀔 때마다 매번 2회씩 새로 학습해야 했는데, 이제는 한 번 글리치가
확인된 세션에서는 훨씬 빠르게 적응합니다.

### 근본적 한계에 대한 솔직한 답변

**완전히 안 뜨게 만드는 건 현재 구조(Photoshop을 외부에서 폴링하는
방식)로는 불가능하다고 판단됩니다.** 이유:
1. 도구 태그 조회(1차 방어)는 `DoJavaScript`로도 실패하는 게 실측
   확인됨 — Photoshop이 바쁜 바로 그 순간엔 어떤 COM 질문도 안
   먹힙니다.
2. 시간 기반 방어(SET 그레이스)는 몇 초짜리 스트로크엔 유효하지만,
   실측된 것처럼 10초 넘게 이어지는 스트로크 앞에서는 무력합니다.
3. 남은 방법(왕복 패턴 학습)은 원리상 **최소 1회의 "학습 비용"**이
   필요합니다 — 처음 보는 색 조합에 대해서는, 그게 글리치인지
   의도적 사용인지 구분할 다른 근거가 전혀 없기 때문입니다.

세션 학습으로 이 학습 비용을 "색 조합마다 매번"에서 "세션당 사실상
한 번"으로 크게 줄였지만, 완전히 0으로 만들 수는 없습니다.

### 외부 색 감지 끄는 방법

1. Photoshop이 실행 중일 때 화면 우상단에 뜨는 **상태 패널**을 찾습니다
   (안 보이면 트레이 아이콘 클릭)
2. 패널의 **톱니바퀴(⚙) 아이콘**을 클릭해서 펼칩니다
3. **"Photoshop 색 변경 자동 감지"** 스위치를 끕니다

꺼도 팝업 안에서 직접 필드를 드래그해서 색을 고르는 기능은 전혀
영향 없습니다 — Photoshop 쪽 변화를 "자동으로 따라가는" 기능만
꺼지는 것이고, 실제 브러시 색에도 영향 없다는 게 이미 확인됐습니다.

## v7.4 변경사항 — 실제 로그로 확인: DoJavaScript도 결국 실패, SET 그레이스 확장으로 대응

### 결정적 확인: 1차 방어(도구 태그)는 근본적으로 작동 불가능

보내주신 로그: `toolName='' tag=PICKING`이 검정이 감지될 때마다 매번
찍혔습니다. `$app.CurrentTool` 직접 접근이든, `DoJavaScript`로
ExtendScript를 돌리든 **똑같이 빈 문자열만 돌아옵니다.**

이건 단순히 "다른 조회 방법을 또 찾아야 한다"는 문제가 아닙니다.
**Photoshop이 바쁜 바로 그 순간엔, `ForegroundColor`뿐 아니라
`DoJavaScript`로 무엇을 물어봐도 똑같이 실패한다**는 뜻입니다. "지금
무슨 도구가 선택돼 있나요?"라고 물어보는 전략 자체가, 정확히 그 답이
필요한 바쁜 순간엔 항상 무력화되는 구조적 한계라는 게 이번에
확정됐습니다. 같은 통신 채널에 다른 질문을 던져봐야 바쁠 땐 어차피
안 돌아옵니다. 이 1차 방어는 사실상 죽은 신호로 판단하고, 코드는
남겨뒀지만(해는 없음) 더 이상 의지하지 않습니다.

### 실측 확인: 2차/3차 방어는 실제로 작동하고 있음

로그를 시간순으로 분석한 결과:
- `04:59:06.598` 검정 감지 → SET 887ms 후라 3차 방어(그레이스)가
  성공적으로 차단
- `04:59:08.805` 검정 감지 → 그레이스(1.5초) 지나서 통과 → 팝업에
  일시적으로 표시됨
- `04:59:12.816` 왕복 2회 확인됨 → 2차 방어가 히스토리에서 소급 제거
  성공
- `04:59:13.319` 검정 감지 → 2차 방어가 즉시 차단 성공

**즉 방어 자체는 작동하고 있고, 문제는 "SET 그레이스 창이 너무
좁아서 두 번째 사례를 놓쳤다"는 것**이었습니다. 실제 타임스탬프를
역산해보니 SET 명령 후 3094ms 시점에도 검정 오독이 있었는데, 그레이스
기간이 1.5초라 못 잡았던 겁니다.

### 수정: SET 그레이스를 1.5초 → 4초로 확장

우리가 직접 통제 가능한 유일하게 확실한 신호(SET 명령 시각)의 창을
넉넉하게 늘렸습니다. 이걸로도 못 잡는 나머지는 이미 실측으로 작동이
확인된 2차 방어(왕복 감지)가 맡습니다.

**검증**: 실제 로그의 정확한 타임스탬프(SET 시각 추정 5711ms, event1
6598ms, event2 8805ms)를 그대로 재현해서, 확장된 그레이스로 **event1과
event2 둘 다 차단**되는 것을 실제 코드로 확인했습니다.

**남은 한계를 솔직히 말씀드리면**: 이번 확장으로 SET 직후 4초 이내의
오독은 대부분 잡히지만, 그보다 더 늦게(예: 색을 고른 지 5초 넘어서)
발생하는 경우는 2차 방어(왕복 학습)에 의존하게 되고, 그 학습 과정에서
최초 1~2회는 팝업에 순간적으로 표시될 수 있습니다(히스토리에는
안 남더라도). 이게 계속 거슬리신다면 v7.3에서 추가한 **"Photoshop 색
변경 자동 감지" 스위치를 끄시는 게 가장 확실한 해결책**입니다 — 실제
브러시 색엔 영향이 없으니까요.

## v7.3 변경사항 — 도구 감지 방식이 조용히 실패했을 가능성 발견 + 감지 자체를 끌 수 있는 설정 추가

### 스크린샷으로 받은 결정적 확인

"펜 촉을 누르고 드로잉을 하는 순간 팔레트가 검은색으로 변해버려 —
**브러시 색이 변하는게 아니라 팔레트의 색이 검은색으로 변하는거야.**
펜 촉을 떼면 다시 팔레트가 원래 색으로 돌아와." 이 확인은 중요합니다
— **실제 그림/브러시 색은 전혀 영향받지 않고, 우리 쪽 팔레트 UI와
히스토리 표시만 일시적으로 검정으로 보이는 것**입니다. 다만
스크린샷의 히스토리에 검정이 여러 개(서로 다른 색들 사이사이) 남아있어서,
v7.2에서 추가한 1차 방어(도구 태그)가 실제로는 작동하지 않고 있다는
의심이 들었습니다.

### 근본 원인 발견: CurrentTool이 COM에서 조용히 실패하고 있었을 가능성

Adobe 커뮤니티 포럼에서 확인된 사실: **"VBS Reference에 없는 속성/
메서드는 Action Manager나 JavaScript를 써야 한다"** — Photoshop의
COM/VBScript 자동화 인터페이스는 ExtendScript DOM보다 훨씬
제한적입니다. `$app.CurrentTool`을 COM 속성으로 직접 읽으려 했던
게, 애초에 COM에 존재하지 않는 속성이라 조용히 예외가 나서(우리 코드의
`try {} catch {}`가 삼킴) **매번 빈 문자열을 반환하고, 그래서 태그가
항상 "PICKING"으로만 나가 1차 방어가 처음부터 무력화돼 있었을
가능성이 높습니다.**

**수정**: COM 속성 직접 접근 대신, 이미 검증된 방식인 **`DoJavaScript`로
ExtendScript(`app.currentTool`)를 실행**해서 도구 정보를 가져오도록
바꿨습니다 — Mac 브릿지에서 AppleScript로 ExtendScript를 실행하는
것과 같은 원리입니다. 검정이 감지될 때마다 실제 toolName 원본값을
진단 로그로 남기도록 했습니다(이전엔 `Write-Host`로 남기려 했는데
Node 쪽에서 stdout을 캡처 안 하고 있어서 로그 자체가 안 찍히는
문제도 함께 발견해서 stderr로 명시적으로 보내도록 고쳤습니다 —
이것도 지금까지 진단이 안 됐던 이유 중 하나일 수 있습니다).

### 실제 작업엔 지장 없음이 확인됐으니, 감지 자체를 끌 수 있는 설정 추가

근본 원인을 고치는 것과 별개로, 확인된 사실(실제 브러시 색은 안

**검증**: 감지를 꺼도 Photoshop 생존 감지(다른 용도)는 그대로
작동하고 색 반영만 멈추는 것을 순수 로직으로, 패널 스위치가 상태를

## v7.2 변경사항 — 3차 방어선(SET 그레이스), Esc 진단 로그 + 방어 코드

### 1. 새로 발견된 패턴: "팔레트 열고 정확히 2번째 터치까지만 검정, 재오픈하면 반복"

**피드백**: "팔레트를 열고나서 처음 터치 시 검은색으로 순간 변경되고,
두번째 터치 시 다시 검은색으로 돼(펜 촉을 떼면 원래 색으로 돌아와)
그리고 세번째 터치부턴 검은색으로 변경되지 않아. 팔레트를 닫고 다시
열면 검은색 인식이 다시 반복돼(2번의 터치까지만)."

**분석**: 이 패턴은 "팔레트를 열자마자 필드에서 색을 고르면(SET 명령
발생) → 그 직후 캔버스를 터치할 때 우리 자신이 보낸 SET 명령과 동시에
진행 중인 폴링 읽기가 서로 충돌"하는 것으로 추정됩니다. 재오픈할
때마다 다시 색을 고르니 SET 명령이 다시 나가고, 그래서 정확히
처음 몇 번만 반복되는 패턴이 설명됩니다.

**수정**: 우리가 마지막으로 SET(전경색 설정) 명령을 보낸 시각을
직접 추적하는 **3차 방어선**을 추가했습니다. 이건 마우스/펜 이벤트에
의존하지 않는, 우리가 100% 확실히 아는 신호입니다 — SET을 보낸 지
1.5초 안에 검정 보고가 오면 태그(1차 방어)와 무관하게 즉시 의심하고
무시합니다.

**검증**: 실제 보고된 정확한 패턴(SET → 첫 터치 검정 → 복귀 → SET →
두번째 터치 검정 → 복귀 → 세번째부턴 정상)을 그대로 재현해서 **검정이
단 1개도 히스토리에 안 남는 것**을 확인했습니다. 기존 1차(도구
태그)·2차(왕복 감지) 방어와 의도적 검정 인정이 이 추가 후에도 전부
정상 작동하는 것도 재검증했습니다.

### 2. Esc로 팝업이 안 닫히는 문제 — 진단 로그 + 방어 코드 추가

코드 리뷰로는 명확한 구조적 버그를 찾지 못했습니다(Esc 처리 로직
자체는 논리적으로 맞아 보임). 다음 재현 시 정확한 원인을 확정할 수
있도록:
- keydown 핸들러 전체를 try/catch로 감쌌습니다 — 이전엔 핸들러 안
  어딘가에서 예외가 나면 조용히 삼켜져서(uiohook 콜백 특성), 그
  이후 로직(Esc 처리 포함)이 실행 안 되는데도 원인을 알 방법이
  없었습니다. 이제 예외가 나면 반드시 로그에 남습니다.
- Esc 키가 감지되는 순간 무조건 `popupVisible` 값을 로그로 남기도록
  했습니다 — uiohook이 Esc를 아예 못 받는 건지, 받았는데
  popupVisible이 이미 false였는지 구분할 수 있습니다.
- `hidePopup()`에 `overlayWin`이 없거나 파괴된 경우에 대한 방어 코드를
  추가했습니다.

**확인 부탁드립니다**: Esc를 눌러도 안 닫히는 상황이 재현되면, 로그
파일에서 `Esc 감지됨...` 줄이 찍혔는지, 그 뒤에 `keydown 핸들러에서
예외 발생...` 같은 에러가 있는지 보내주세요. 이걸로 정확한 원인을
확정하고 근본적으로 고칠 수 있습니다.

### 핵심 아이디어: 단발성인지 반복되는지로 구분

실제 로그로 확인된 사실: 펜을 꾹 누르고 있는 동안엔 Photoshop이 계속
바쁜 상태라 **"색X → 검정 → 색X" 왕복이 폴링마다 계속 반복해서
재발**합니다. 반면 사용자가 의도적으로 검정을 한 번 쓰는 건, 그 뒤에
어떤 색으로 가든 "같은 조합의 왕복"이 반복될 이유가 없습니다. 이 차이가
글리치와 의도적 사용을 구분하는 가장 정확한 신호입니다.

**동작 방식**: 검정은 **항상 즉시 적용**합니다(의도적 사용이 지연 없이
반영되도록). 다만 "색X → 검정 → 색X" 왕복이 짧은 시간(6초) 안에 **같은
색 조합으로 2번째 재발**하면, 그건 확실히 반복 글리치로 확정하고 —
그 시점부터는 같은 조합의 검정을 아예 적용하지 않고, 방금 반복을
확정시킨 검정 항목도 히스토리에서 지웁니다. 펜을 계속 누르고 있어서
왕복이 계속 재발하는 동안은 **유효기간이 계속 연장되는 슬라이딩
윈도우**를 써서, 아무리 오래 눌러도(6초 이상) 억제가 풀리지 않습니다.

### 검증 중 실제로 잡은 버그 두 개

1. **조기 억제 버그**: "이미 확정됨" 체크에 `watchedCount >= 2` 조건이
   빠져서, 1번째 왕복만으로 성급하게 무시해버려 2번째 사이클이 완성될
   기회 자체가 없었습니다.
2. **고정 윈도우 버그**: 유효기간이 최초 발생 시점에서 고정돼 있어서,
   펜을 6초 넘게 누르고 있으면 창이 만료돼 감지가 리셋되고 검정이 한
   번 더 새어나갔습니다 — 실제로 20초 반복 시뮬레이션 테스트로 이
   버그를 잡아냈습니다. 재발할 때마다 유효기간을 연장하는 슬라이딩
   윈도우로 고쳤습니다.

**검증**: 네 가지 핵심 시나리오를 순수 로직으로 확인했습니다.
- 의도적 단발성 검정(빠르게 찍고 복귀) → 히스토리에 정상적으로 남음
- 검정을 쓰다가 완전히 다른 색으로 → 정상적으로 남음
- **펜을 20초간 눌러 왕복이 10번 반복되는 긴 글리치** → 최초 1개만
  남고 나머지 9번은 전부 억제됨(수정 전엔 6초 창 만료로 2개가 샜음)
- 검정과 무관한 일반적인 색 작업 → 전혀 영향 없음

복귀하는 경우엔 소급 제거가 안 될 수 있습니다(v6.6~v6.7에서 확인된
긴 글리치 사례처럼). 이건 "글리치인지 의도적 사용인지"를 완벽하게

확실한 방법을 원하시면 팝업 안 필드에서 직접 검정을 고르시는 걸
권합니다(그 경로는 이 문제와 완전히 무관합니다).

## v6.8 변경사항 — 검정 필터링 단순화(오탐 제거), z-order 대신 실제 hide/show로 전환

### 1. 의도적인 검정까지 히스토리에서 지워지던 문제 — 규칙을 훨씬 단순하게

show)** 하는 방식으로 완전히 교체했습니다. 안 보이는 창은 어떤 창도
가릴 수 없으니 훨씬 확실합니다. `popupVisible`(사용자가 "열어뒀다"고

**검증**: Photoshop 활성/비활성에 따라 팝업·패널이 정확히 보이고
숨는 것, 비활성 시엔 확실히 안 보이는(다른 창을 절대 가릴 수 없는)

확인했습니다.

## v6.7 변경사항 — 검정 오독 근본 개선(소급 정정), 팔레트가 뒤로 숨는 문제 진단+완화+수동 복구

### 1. "1.5초 넘게 누르면 검정으로 인식" — 시간 기반 방식의 한계를 소급 정정으로 보완

**중요한 재확인**: 이 경로(외부 색 변경 감지)는 Photoshop이 보고하는
값을 **읽기만** 하고, 우리가 Photoshop에 색을 쓰는 경로가 아닙니다

뿐입니다.** 이걸 확인하고 나니, 확정 대기 시간을 넉넉하게 잡아도

지장이 없다는 걸 알 수 있었습니다.

**수정**: 확정 대기 시간을 600ms → **1800ms**로 늘려서 짧은 오독은
더 확실히 걸러내고, 그래도 그 시간을 넘겨서 "검정"이 일단 인정되는
경우를 위해 **소급 정정**을 추가했습니다 — 검정을 인정한 뒤에도 5초
안에 그 검정 이전에 있던 색으로 다시 돌아오면, "그 검정은 오독이었다"고
뒤늦게 판단해서 히스토리에서 자동으로 지웁니다.

**검증**: 실제 색 → (오래 눌러서) 검정 확정 인정 → 펜을 떼서 원래
색으로 복귀, 이 순서를 그대로 재현해서 검정 히스토리 항목이 정확히
소급 제거되는 것을 확인했습니다.

### 2. 팔레트가 Photoshop 뒤로 숨는 문제 — 진단 로그 + 반응 속도 완화

**분석**: `isPhotoshopActive()`는 활성 창의 프로세스명/제목에
"photoshop"이 포함돼야만 활성으로 인식합니다. Photoshop이 띄우는
특정 대화상자(색상 피커, 필터 갤러리 등)가 제목에 "Photoshop"이
없으면 오탐될 수 있고, 지난 버전에서 반응 속도를 75% 빠르게(0.3초)
만든 게 이런 순간적인 오탐을 훨씬 도드라지게 만들었을 가능성이
있습니다.

**수정**: 
- `isPhotoshopActive()`가 "비활성"으로 판단할 때마다 그 순간의 실제
  활성 창 정보(프로세스명/제목)를 로그로 남기도록 했습니다 — 다음에
  재현되면 정확히 어떤 창 때문인지 바로 알 수 있습니다.
- 반응 속도를 0.3초 → **0.6초**로 살짝 완화했습니다(그래도 예전
  1.2초보단 2배 빠름) — 너무 민감했던 게 오탐에 취약하게 만들었을
  가능성을 감안한 균형 조정입니다.

### 3. 트레이 아이콘 클릭 시 즉시 강제 복귀 (수동 안전장치)

**관찰**: "트레이를 누르면 다시 앞으로 돌아온다"는 게 우연이 아니라
의도된 기능이 되도록 만들었습니다. 트레이 아이콘을 클릭하면(메뉴

앞으로 강제 복귀시킵니다 — 자동 감지가 어떤 이유로든 잘못된 상태에
갇히더라도 클릭 한 번으로 확실히 복구할 수 있는 수동 수단입니다.

**검증**: 두 창이 오탐으로 뒤로 가있는 상태에서 트레이 클릭 시 정확히
둘 다 다시 앞으로 오고, 디바운스 카운터도 함께 리셋되는 것을
확인했습니다.

**확인 부탁드립니다**: 이번에도 팔레트가 뒤로 숨는 상황이 재현되면,
로그 파일에서 `isPhotoshopActive=false 판정. 실제 활성 창:
execName="..." title="..."` 부분을 찾아서 보내주세요 — 정확히 어떤
창이 오탐을 일으키는지 확정되면 그 창을 예외 처리해서 근본적으로
막을 수 있습니다.

## v6.6 변경사항 — 로그로 확정된 펜-검정 오독 원인, 완전히 다른 방식으로 재설계 + 항상위 반응 속도 개선

### 결정적 증거: 펜 입력에서 mousedown/mouseup이 아예 안 찍힘

사용자가 보내주신 로그를 분석한 결과, **12:04:33~12:04:53까지 20초
동안 펜으로 계속 그리고 계셨을 텐데 `mousedown`/`mouseup` 이벤트가
단 한 번도 로그에 안 찍혔습니다.** 이건 이 사용자의 태블릿이 Wintab
등의 방식으로 Windows 표준 마우스 메시지 파이프라인을 건너뛰고
Photoshop에 직접 입력을 전달한다는 확정적 증거입니다 — `uiohook`은
표준 마우스 후킹 기반이라 이런 입력을 원천적으로 감지할 수 없습니다.
즉 v6.5에서 만든 `mouseButtonDown` 게이트는 **이 환경에서 펜에 대해
절대 작동할 수 없는 구조**였습니다.

### 재설계: 마우스 이벤트가 아니라 "패턴" 자체를 의심

`com-bridge.js`의 폴링 코드를 다시 보니, `$app.ForegroundColor.RGB`
읽기가 실패해도 `catch {}`가 조용히 넘어가는 부분이 있어서, Photoshop이
스트로크 처리로 바쁠 때 색상 객체가 아직 초기화 안 된 "빈 값"(RGB
전부 0)이 예외 없이 정상값처럼 읽힐 가능성이 있습니다 — 이게 왜
검정이 찰나가 아니라 몇 초씩 안정적으로 지속되는지도 설명이 됩니다.

**완전히 새 접근**: 마우스가 눌려있는지가 아니라, **색이 갑자기
검정으로 튀는 패턴 자체**를 의심합니다. 검정이 아닌 색을 쓰다가 갑자기
검정 보고가 오면 곧바로 반영하지 않고 600ms 확정 대기 타이머를 겁니다.
그 사이에 다른(검정 아닌) 보고가 오면 방금 그 검정은 오독이었다고
확정하고 타이머를 취소합니다. 반대로 그 시간 동안 계속 검정 상태가
유지되면(=진짜 사용자가 고른 검정으로 판단) 그제서야 적용합니다.
기존 `mouseButtonDown`/그레이스 기간 게이트는 일반 마우스 사용자에게는
여전히 유효하니 그대로 두고, 이 새 방어층을 추가로 얹었습니다.

**검증**: 실제 로그의 정확한 패턴(실제색 → 700ms 후 검정 글리치 →
900ms 시점에 실제색 복귀)을 그대로 재현해서, 검정이 단 한 번도
적용되지 않는 것을 확인했습니다. 반대로 사용자가 진짜 검정을 골라서
이후 아무 변화가 없는 경우, 600ms 뒤 정상적으로 검정이 적용되는 것도
확인했습니다.

### 항상위 반응 속도 75% 개선

**문제**: 다른 창(카톡 등)으로 전환해도 팔레트가 계속 앞에 떠 있다는
피드백 — 감시 주기(400ms) × 필요 연속 횟수(3) = 최대 1.2초나 걸려서
체감 지연이 컸습니다. COM 브릿지가 이제 상시 연결(TCP)이라 예전만큼
넉넉한 디바운스가 필요 없어서, **150ms × 2 = 최대 0.3초**로 줄였습니다
(75% 개선).

## v6.5 변경사항 — 펜으로 꾹 누르면 검은색으로 오독되는 문제, 진단 로그 + 방어 추가

**증상**: 펜으로 꾹 누르고 있으면 색이 순간적으로 검은색으로 바뀌고
그게 히스토리에까지 남으며, 떼면 원래 색으로 돌아온다.

**분석**: v4.6에서 이미 이 문제(스트로크 도중 COM 폴링이 검은색을
오독)를 막으려고 `mouseButtonDown` 게이트를 추가했었는데, 그게
정확히 눌려있는 동안만 재현된다는 건 **그 게이트가 펜 입력에서는
실제로 작동하지 않고 있다는 뜻**입니다. 원인 후보 두 가지:

1. 펜 터치가 uiohook에 `LEFT_MOUSE_BUTTON`(1)이 아닌 다른 번호로
   들어와서 게이트 자체가 안 걸림
2. **Wacom 등 일부 태블릿이 "Wintab" 드라이버 모드에서 압력 감지
   입력을 Photoshop에 직접 전달하고, Windows 표준 마우스 메시지
   파이프라인 자체를 건너뜁니다** — 이 경우 uiohook(표준 마우스 후킹
   기반)은 펜 입력을 이벤트 자체를 감지 못합니다.

**수정**: 정확한 원인을 확정하기 위해 진단 로그를 추가했습니다 —
모든 `mousedown`/`mouseup`의 `e.button` 값, 그리고 색 보고가 올 때마다
그 순간의 `mouseButtonDown` 상태를 전부 로그에 남깁니다. 동시에
**mouseup 이후 150ms 그레이스 기간에도 색 보고를 의심하는 추가
방어층**을 넣었습니다(뗀 직후 살짝 늦게 들어오는 오독까지 방어).

**검증**: 스트로크 중 색 보고 5번이 전부 무시되는 것, 뗀 직후
그레이스 기간(150ms) 안에는 여전히 무시되는 것, 그 이후엔 정상
적용되는 것을 순수 로직으로 확인했습니다.

**확인 부탁드립니다**: 펜으로 꾹 눌러서 증상을 재현해보시고, 로그
파일에서 `mousedown 감지: e.button=...`과 `색 변경 보고 수신:
... mouseButtonDown=...`이 어떻게 찍히는지 보내주세요. `e.button`이
1이 아니거나, mousedown 로그 자체가 아예 안 찍힌다면 위 원인 중
어느 쪽인지 바로 알 수 있습니다.

**수정**: 팝업(핀 여부 무관하게 항상)과 상태 패널 둘 다에 동일한
규칙을 적용했습니다 — Photoshop이 활성 앱일 때만 "항상 위"를 켜고,
다른 앱(카톡, 브라우저 등)으로 전환되면 항상 위를 끕니다. 창을
닫는(hide) 게 아니라 z-order만 조정하는 방식이라, Photoshop으로
돌아오면 재계산 없이 즉시 그 자리에 다시 나타납니다. 기존에 위치
고정 전용이었던 로직을 `syncAlwaysOnTop()` 공통 함수로 일반화해서
두 창에 동일하게 적용했습니다.

**검증**: 팝업과 패널이 둘 다 열린 상태에서 Photoshop 비활성이 연속
감지되면 둘 다 항상위만 꺼지고(닫히지 않음), Photoshop으로 복귀하면
둘 다 다시 켜지는 것, 팝업이 애초에 안 열려있으면 그쪽 상태는 안
건드리고 패널은 독립적으로 계속 반응하는 것을 순수 로직으로
확인했습니다.

### 2. 활성화 트리거를 다시 누르면 닫히는 토글 (설정 가능)

**요청**: 트리거(예: 중클릭)를 팝업이 열린 상태에서 한 번 더 누르면
닫히게 해달라. 다만 이게 항상 원하는 동작은 아닐 수 있으니 조정
가능하게 해달라.

**구현**: 새 설정 `config.triggerTogglesClose`(기본값 `true`)를
추가했습니다. 켜져 있으면 트리거(마우스 버튼이든 키보드 키든)를
팝업이 열린 상태에서 다시 입력했을 때 `hidePopup()`이 호출됩니다.
꺼져 있으면 기존처럼 "열기 전용"으로 동작합니다. 좌클릭을 트리거로
쓰는 경우 브러시질 도중 매 클릭마다 닫힘이 걸리는 걸 원치 않을 수
있어서, 상태 패널의 펼침 섹션에 **"트리거를 다시 누르면 닫기"**
스위치를 추가해서 언제든 켜고 끌 수 있게 했습니다.

**검증**: 토글이 켜져 있을 때 트리거를 두 번 누르면 열림→닫힘이
정확히 일어나는 것, 토글이 꺼져 있을 때는 이미 열린 상태에서 몇 번을
더 눌러도 안 닫히는 것을 순수 로직으로 확인했습니다. 패널의 새
스위치가 main으로부터 초기값을 정확히 반영하는 것, 사용자가 스위치를
바꾸면 정확한 값으로 저장 요청이 가는 것을 jsdom으로 확인했습니다.

## v6.1 변경사항 — 위치 고정 시 다른 창 전환해도 안 꺼짐, 패널 최소화/리사이즈

### 1. 위치 고정 상태에서 카톡 등 다른 창으로 가도 팔레트가 안 꺼짐

**요청**: 핀으로 고정했으면, 카톡이나 다른 창을 열어도 팔레트가 꺼지지
않게 해달라. 단, Photoshop 안에서만 켜져있어야 하고 브라우저 등 다른
창보다 앞에 있으면 안 된다.

**구현**: 기존엔 Photoshop이 비활성 상태로 일정 시간 지속되면 무조건
`hidePopup()`으로 팝업을 완전히 닫았습니다. 이제 **위치 고정 상태일
때는 팝업을 닫지 않고, 대신 "항상 위" 속성만 껐다 켰다** 합니다 —
Photoshop이 비활성화되면 `setAlwaysOnTop(false)`로 다른 창(카톡,
브라우저)보다 앞에 뜨지 않게 하고, Photoshop으로 돌아오면
`setAlwaysOnTop(true)`로 다시 앞에 나옵니다. 팝업 자체는 계속
열려있는 상태라, Photoshop으로 돌아오면 재계산 없이 즉시 그 자리에
다시 나타납니다. 위치 고정을 안 한 경우엔 기존 동작(자동으로 닫힘)이
그대로 유지됩니다.

**검증**: 위치 고정 상태에서 비활성이 연속 4회 감지돼도 팝업이 안
꺼지고 항상위만 꺼지는 것, Photoshop으로 돌아오면 항상위가 다시
켜지는 것, 위치 고정을 안 했을 때는 기존처럼 실제로 닫히는 것을
순수 로직으로 확인했습니다.

### 2. 상태 패널 최소화 + 크기 조절

**최소화**: 패널 상단에 최소화 버튼(─)을 추가했습니다. 누르면 패널이
작은 원형 점 하나로 줄어들고(신뢰도 표시등은 그 점에도 그대로
반영됩니다), 그 점을 클릭하면 원래 크기로 정확히 복귀합니다.

**크기 조절**: `resizable: false` → `true`로 바꿔서, 패널 가장자리를
드래그해 원하는 크기로 조절할 수 있습니다. 사용자가 조절한 크기는
톱니바퀴로 단축키 섹션을 펼치거나 접어도, 최소화했다가 복귀해도
그대로 유지됩니다 — `positionStatusPanel()`을 "위치(x/y)만 재계산"과
"크기를 명시적으로 바꾸는 것"으로 분리해서, 의도치 않게 사용자의
리사이즈를 덮어쓰지 않도록 했습니다.

**검증**: 사용자가 500×120으로 리사이즈했다고 가정한 뒤 최소화(40×40)
했다가 복귀시켰을 때 정확히 500×120으로 돌아오는 것을 확인했습니다.
최소화 버튼 클릭 시 렌더러의 `is-minimized` 클래스가 정확히 붙고
main에 요청이 가는 것, 최소화된 점을 클릭하면 정확히 복귀 요청이
가는 것, 신뢰도 실패 상태가 최소화된 점에도 반영되는 것을 jsdom으로
확인했습니다.

## v6.0 변경사항 — macOS 지원 추가 (AppleScript 브릿지)

### 핵심 아키텍처: 플랫폼별 브릿지 자동 선택

`com-bridge.js`(Windows, PowerShell+COM)와 완전히 동일한 공개
인터페이스(`startBridge`/`setForegroundColor`/`activateTool`/
`testConnection`/`stopBridge`)를 가진 `mac-bridge.js`를 새로 만들었습니다.
`main.js`는 `process.platform`에 따라 둘 중 하나를 자동으로 골라
require하고, 나머지 코드는 전혀 손댈 필요가 없습니다.

### mac-bridge.js — AppleScript로 ExtendScript 엔진 호출

Windows에서 PowerShell + COM을 썼던 것처럼, macOS에서는 `osascript`로
`tell application "Adobe Photoshop 2025" to do javascript "..."`를
실행해서 Photoshop의 **ExtendScript 엔진**을 호출합니다. Windows COM
브릿지와 **정확히 같은 Action Manager 방식**(`executeAction` +
`ActionDescriptor`/`ActionReference`)으로 전경색을 설정합니다 —
직접 프로퍼티 대입이 아니라 이 방식을 쓴 이유(최신 Photoshop에서
직접 대입이 안 먹는다는 보고)를 그대로 이어받았습니다.

Photoshop이 안 켜져 있을 때 자동으로 실행돼버리는 COM의 부작용과 같은
문제를 막기 위해, `System Events`로 프로세스 존재 여부를 먼저 확인한
뒤에만 Photoshop에 말을 겁니다.

**⚠️ 검증 안 됨**: 이 코드는 실제 macOS + Photoshop 환경에서 테스트하지
못했습니다(이 작업 환경엔 macOS 자체가 없음). ExtendScript 문법과
Action Manager 로직 자체는 Windows에서 검증된 것과 동일한 원리를
그대로 옮긴 것이지만, 실제로 돌려보시고 콘솔의 `[mac-bridge]` 로그를
그대로 알려주시면 바로 고치겠습니다.

**검증한 것**: RGB 값이 ExtendScript 코드에 정확히 삽입되는 것, 개행이
전부 제거돼 한 줄로 만들어지는 것(AppleScript `-e` 인자 안정성),
AppleScript 문자열 리터럴의 큰따옴표 이스케이핑이 정확히 짝이 맞는
것(4개 — `tell application "..."` 2개 + 전체를 감싸는 `"..."` 2개)을
확인했습니다. `osascript` 자체가 없는 이 환경에서 호출을 시도했을 때도
크래시 없이 에러가 정상적으로 로그되는 것도 확인했습니다.

### 실제 macOS 빌드까지 성공

`@miniben90/x-win`이 Mac(Intel/Apple Silicon)을 공식 지원하는 것을
확인하고, `npm install --os=darwin --cpu=x64`로 Mac용 네이티브
바이너리를 명시적으로 받은 뒤, **실제로 electron-builder로 Mac용
패키지(x64 + arm64 zip)를 이 환경에서 끝까지 빌드했습니다.**
`uiohook-napi`, `@miniben90/x-win`의 macOS 네이티브 바이너리(`.node`)와
`.ccx` 리소스가 전부 패키징된 `.app`에 정상 포함된 것을 직접 확인했습니다.

**DMG는 못 만들었습니다** — macOS 설치파일의 표준 형식인 DMG는
`iconv-corefoundation`이라는, **실제 macOS에서만 실행 가능한 네이티브
도구**가 있어야 만들 수 있습니다(Windows의 NSIS와 달리 Wine으로도
우회가 안 되는 진짜 macOS 전용 영역). 그래서 이번엔 `.app.zip` 형태로
빌드했습니다 — 압축 풀면 바로 실행 가능한 `.app`이 나오니 배포 자체는
가능하지만, 정식 DMG 설치 경험을 원하시면 실제 Mac에서
`npm run dist -- --mac`을 한 번 더 돌리셔야 합니다(그러면 자동으로
DMG까지 만들어집니다 — macOS에서 실행하면 이 제약 자체가 없음).

**코드사이닝도 못 했습니다** — 이것도 실제 macOS + Apple Developer
인증서가 있어야 하는 작업이라(`skipped macOS application code signing
reason=supported only on macOS`라고 electron-builder가 스스로
건너뛴 것으로 확인), 이 상태로 배포하면 Gatekeeper가 "확인되지 않은
개발자" 경고를 띄웁니다. 정식 배포 전에는 Apple Developer Program
가입 후 코드사이닝 + 공증(notarization) 절차가 필요합니다.

**추가한 것**:

**검증**: 적용 실패 시 `bridgeHealthy`가 즉시 `false`로 바뀌고 팝업에

방지를 위한 `app.exit()` 기반 종료까지 지난 라운드에서 검증된 로직을
그대로 보존했습니다.

## v4.21 변경사항 — 명령 처리 지연(초 단위) 원인 발견, 설치 후 자동실행 끄기, 미실행 상태 오탐 방지

### 1. 명령 하나 처리에 2~6초씩 걸리던 문제

**원인**: `Test-PhotoshopRunning`(내부적으로 `Get-Process`로 전체
프로세스 목록을 뒤짐)이 **한 루프 반복(100ms)마다 최대 4번**씩
불리고 있었습니다. `Get-Process`는 생각보다 무거운 작업이라, 이렇게
자주 부르면 루프 자체가 밀려서 대기 중인 명령 처리가 몇 초씩 지연되는
원인이 됐을 가능성이 큽니다. 실제 로그에서 `SET` 명령 하나가 3.8초,
5.3초, 심지어 6초 타임아웃까지 걸리는 게 관찰됐습니다.

**수정**: `Get-Process`를 매번 실제로 부르지 않고, **800ms에 한 번만
실제로 조회하고 그 사이엔 캐시된 값을 재사용**하도록 바꿨습니다.

**검증**: 100ms 루프를 2초(20회, 반복당 2번씩 총 40번 요청) 도는
상황을 재현했을 때, 실제 `Get-Process` 호출이 **40번 → 2번**으로
줄어드는 것을 확인했습니다.

### 2. 설치 후 자동 실행 끄기

`electron-builder`의 NSIS 설정에서 `runAfterFinish`를 `true → false`로
바꿨습니다. 이제 설치가 끝나도 자동으로 실행되지 않고, 사용자가 직접
실행 파일/바로가기를 실행해야 켜집니다.

### 3. Photoshop을 아직 한 번도 못 본 상태에서 오탐으로 자동 종료되던 문제

**원인**: (2번 설정 변경 전에는) 설치 직후 자동 실행됐을 때, 혹은
그냥 Photoshop보다 SHA Paint를 먼저 켰을 때 — Photoshop이 **아직 한
번도 켜진 적이 없는데도** "없다"고 계속 판단해서 몇 초 만에 "종료됨"
알림과 함께 SHA Paint가 스스로 꺼져버렸습니다.

**수정**: PowerShell 쪽에 Photoshop이 실행 중임을 **처음** 확인하면
보내는 `PS_ALIVE` 신호를 새로 추가했습니다. main 프로세스는 이 신호를
**한 번이라도 받기 전까지는** "Photoshop이 없어졌다"는 판단 자체를
무시합니다 — 즉 "있다가 없어진 것"과 "애초에 아직 안 켰다"를 구분해서,
후자는 종료 트리거로 안 씁니다.

**검증**: Photoshop을 한 번도 안 켠 채로 "없음" 신호를 20번 연속 받아도
종료가 안 되는 것, 이후 Photoshop을 실제로 켰다가(PS_ALIVE 수신) 진짜로
끄면(연속 8번 "없음") 정상적으로 종료 판단되는 것을 확인했습니다.

## v4.20 변경사항 — "종료했는데 반쯤 살아있는" 좀비 상태 버그 발견 및 수정

### 발견 경위

사용자가 트레이 메뉴에서 "종료"를 눌렀는데, 로그를 보니:
```
[overlay] 종료: 사용자가 트레이 메뉴에서 종료
[com-bridge] 소켓 에러: read ECONNRESET
[com-bridge] PowerShell 브릿지 연결 끊김
```
여기까지는 정상(정리 작업이 실행된 증거)인데, 그 **몇 초 뒤에도 계속
팝업이 열리고 색을 고르는 등 앱이 여전히 반응**했습니다 — "종료"를
눌렀는데 실제로는 안 꺼지고, COM 브릿지만 죽은 채로 나머지는 계속
살아있는 좀비 상태가 된 것입니다.

### 원인

Electron 공식 문서를 확인한 결과: `app.quit()`는 특정 상황에서 **확실하게
프로세스를 끝낸다는 보장이 없는**, 실제로 보고된 적 있는 Electron의
함정입니다. `will-quit` 이벤트까지는 정상적으로 발생해서 저희 정리
코드(COM 브릿지 종료 등)는 실행됐지만, 그 이후 실제 프로세스 종료가
어떤 이유로 완료되지 못하고 멈춰버린 것으로 보입니다.

### 수정

정리 작업과 종료 방식을 분리했습니다:
1. **정리 작업**(키보드/마우스 후킹 해제, WS 서버 닫기, COM 브릿지
   프로세스 종료)을 `cleanupBeforeExit()` 함수로 모아서, 종료 직전에
   **직접 동기적으로** 실행합니다.
2. `app.quit()` 대신 **`app.exit(0)`**을 씁니다 — 이건 생명주기
   이벤트를 기다리지 않고 프로세스를 즉시 강제 종료하는 확실한
   방법입니다. (그래서 정리 작업을 그 *전에* 직접 실행해야 합니다 —
   안 그러면 PowerShell 프로세스가 좀비로 남을 수 있어서, 순서가
   중요합니다.)
3. `will-quit` 이벤트 핸들러도 같은 정리 함수를 재사용하도록 정리했고,
   우리가 직접 트리거하지 않은 다른 종료 경로(OS 로그아웃 등)에 대한
   안전망으로 남겨뒀습니다. 정리 함수는 중복 호출돼도 안전합니다(이미
   정리된 건 다시 안 건드림).

**검증**: 정리 작업이 먼저 실행된 뒤 종료가 호출되는 순서, 그리고
정리 함수를 중복으로 불러도 에러 없이 안전한 것을 확인했습니다.

### 이전 "연결이 계속 안 됨" 문제와의 연관 가능성

이 좀비 상태 버그가 어쩌면 이전에 겪으신 "PowerShell 브릿지 연결이
계속 안 됨" 문제의 **진짜 원인**이었을 수 있습니다 — "종료"했다고
생각한 이전 SHA Paint 인스턴스가 실제로는 백그라운드에 좀비로 남아서
TCP 포트(51900)를 계속 붙잡고 있었다면, 새로 실행한 인스턴스의
PowerShell이 그 포트에 붙으려다 실패하거나 엉뚱한 좀비 서버에 연결됐을
수 있습니다.

**한 번만 확인해주시면 좋겠습니다**: 작업관리자에서 "SHA Paint" 또는
"electron.exe" 관련 프로세스가 **여러 개** 떠 있지는 않은지 확인해서,
있다면 전부 종료한 뒤 새 버전으로 딱 하나만 실행해서 테스트해주세요.

## v4.19 변경사항 — "갑자기 또 연결 안 됨" 문제 방어 로직 추가

**증상**: 이전엔 정상 작동(1~2ms 응답)하다가, 어느 시점부터 계속
`아직 연결 안 됨, 명령 무시`만 뜨고 `PowerShell 브릿지 연결됨` 로그가
전혀 안 보임 — PowerShell 클라이언트가 이 세션 동안 한 번도 연결에
성공 못 한 것으로 보입니다.

**추가한 방어 장치 두 가지** (근본 원인은 로그가 더 필요해서 아직
확정 못 했지만, 이 상황 자체를 자동으로 복구하도록):

1. **연결 감시(watchdog)**: PowerShell 프로세스가 죽지 않았는데도(그러면
   기존 재시작 로직이 안 걸림) 8초 안에 연결이 안 되면, 그 프로세스를
   강제로 죽여서 기존 재시작 경로(3초 뒤 재시도)를 타게 만듭니다. 즉
   "프로세스는 살아있는데 어쩐지 연결만 안 되는" 상황이 생겨도 최대
   8초 안에 자동으로 복구를 시도합니다.
2. **`TcpClient.Connect()` 실패 원인 로그**: 지금까지는 연결 자체가
   실패해도 이유가 전혀 안 남았을 가능성이 있습니다(스크립트가 그냥
   조용히 죽었을 수 있음). 이제 `Connect()`를 try/catch로 감싸서, 실패
   시 `CONNECT_ERR: ...` 형태로 정확한 이유를 stderr에 남기고, 이건
   그대로 로그 파일에도 찍힙니다.

**검증**: 프로세스가 죽지 않고 연결도 안 되는 상황을 재현해서, 설정한
시간이 지나면 워치독이 정확히 발동하는 것을 확인했습니다.

**확인 부탁드립니다**: 이번에 또 같은 증상이 나오면, 이제
`CONNECT_ERR` 로그나 `연결 감시: ... 강제 재시작` 로그가 남을 겁니다.
그 내용을 그대로 알려주시면 진짜 근본 원인(방화벽/보안 프로그램이
localhost 연결을 막는지, 포트 충돌인지 등)을 확정할 수 있습니다.

## v4.16 변경사항 — "지금 당장 흐름을 끊는 것들" 세 가지 전부 개선

### 1. 속도 — TCP 소켓 기반 상시 연결로 재설계 (600ms~1초 → 1~수십ms)

**원인**: 색 하나 적용할 때마다 PowerShell 프로세스를 처음부터 새로
띄우고 있었다. PowerShell 자체를 시작하는 고정 비용(.NET 런타임 초기화
등)이 대부분의 시간을 차지했다.

**재설계**: stdin 파이프 대신 **로컬 TCP 소켓**으로 Node ↔ PowerShell을
연결했다. PowerShell 프로세스 하나가 앱 실행 중 **딱 한 번만** 뜨고,
COM 객체($app)도 딱 한 번만 만들어서 계속 재사용한다. 그 프로세스의
메인 루프가 `NetworkStream.DataAvailable`(신뢰할 수 있는 논블로킹 확인
— 예전에 문제였던 `Console::In.Peek()`과 달리 이건 파이프 stdin의
버퍼링 문제가 없음)로 소켓의 명령을 확인하는 것과, 전경색을 폴링하는
것을 같이 돈다.

**검증**: 실제 TCP 서버(com-bridge.js 그대로)에 순수 Node로 만든 "가짜
PowerShell" 클라이언트를 연결해서 end-to-end로 확인했다 —
`setForegroundColor` 응답이 **1~2ms**로 왔고(이전 600~1000ms 대비
수백 배), 연속으로 SET/TOOL/TEST를 빠르게 보내도 FIFO 큐가 정확한
순서로 응답을 매칭했다. PowerShell 실행 파일 자체는 이 환경에 없어서
(리눅스 샌드박스) 진짜 COM 호출까지 포함한 왕복 시간은 검증 못 했지만,
Node 쪽 오버헤드는 사실상 0에 가깝다는 게 확인됐다.

### 2. 클릭 추적 모드가 브러시와 충돌하던 문제 — 트리거를 중클릭으로 변경

**문제**: 클릭 추적 모드(F9)가 좌클릭으로 팝업을 열었는데, 이건 브러시가
쓰는 바로 그 클릭이라 그림을 그리기 시작하는 순간 팝업이 뜨면서
스트로크를 가로챌 위험이 있었다.

**수정**: 클릭 추적 모드의 트리거를 **중클릭**으로 바꿨다. 브러시(좌클릭)
와 절대 겹치지 않아서, 켜놔도 그림 그리는 데 지장이 없다. 좌클릭 자체는

## v4.14 변경사항 — 브러시 색 적용 성공 확인! 남은 신뢰성/속도/인코딩 문제 수정

**사용자 확인**: v4.13 이후 **팔레트에서 고른 색이 실제로 브러시에
적용됩니다!** 다만 스포이드/팔레트 선택 둘 다 반응이 약 1초 정도
느리게 느껴진다는 피드백과 함께, 로그에서 두 가지 구체적인 문제를
확인했습니다.

### 1. `RPC_E_SERVERCALL_RETRYLATER` — COM 서버가 순간적으로 바쁨

이 HRESULT는 "Photoshop의 COM 서버가 지금 바쁘니 나중에 다시
시도하라"는 표준 COM 신호입니다. 감시(폴링) 프로세스가 500ms(이전엔
300ms)마다 같은 COM 서버에 접근하는 것과, 색을 설정하는 명령이 순간적으로
경합하는 것으로 보입니다.

**수정**: `setForegroundColor`/`activateTool` 안에 **자동 재시도
루프**(최대 5회, 실패 시 150ms 대기 후 재시도)를 추가했습니다. 이제
"바쁨" 신호를 받아도 조용히 재시도해서, 이전처럼 픽이 조용히 유실되는
일 없이 대부분 성공할 겁니다. 폴링 주기도 300ms→500ms로 늘려서 애초에
경합이 덜 나도록 했습니다.

### 2. `Count Application ObjectValue ... SET_OK` — 반환값 자동 출력 버그

PowerShell은 대입되지 않은 표현식의 결과를 자동으로 출력 스트림에
써버립니다. `$a.ExecuteAction(...)`이 반환하는 `ActionDescriptor`
객체를 저희가 그냥 버리지 않고 있어서, 이게 `SET_OK`보다 먼저 출력에
섞여 나갔고, 그래서 저희 코드가 "SET_OK"를 정확히 못 알아보고 "알 수
없는 응답"으로 처리했던 것입니다.

**수정**: `[void]$a.ExecuteAction(...)`으로 반환값을 명시적으로
버리도록 했습니다. 이제 출력엔 저희가 의도한 한 줄(`SET_OK` 또는
`SET_ERR ...`)만 나갑니다.

### 3. 한글 에러 메시지 깨짐 (인코딩)

Windows 한글 로케일에서 COM 예외 메시지가 시스템 기본 코드페이지(주로
CP949)로 나오는데, Node.js가 기본적으로 UTF-8로 디코딩해서 글자가
깨져 보였습니다.

**수정**: 모든 PowerShell 스크립트 맨 앞에
`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`을 추가해서,
출력 자체를 UTF-8로 강제했습니다.

**검증**: 새 응답 처리 로직(정상 성공/재시도 후 최종 실패 케이스)이
정확히 파싱되는 것을 확인했습니다. 재시도 루프와 `[void]` 처리 자체는
PowerShell 코드라 이 환경(Photoshop 없음)에서 직접 실행 검증은
불가능했습니다 — 실제로 돌려보시고 여전히 "알 수 없는 응답"이나 반응
속도 문제가 남아있으면 로그와 함께 알려주세요.

## v4.13 변경사항 — 진짜 원인 발견: PowerShell stdin의 Peek() 신뢰성 문제

**사용자가 보내주신 로그가 결정적이었습니다.** 파이프라인 전체에 로그를
심은 덕분에 정확히 어디서 끊기는지 확인됐습니다:

```
[com-bridge] 명령 전송: SET 177,205,122
(... 이후 SET_OK도 SET_ERR도 전혀 없이 조용히 사라짐, 4번 다 동일)
```

그런데 그 직전에 보낸 `TEST` 명령은 정상적으로 응답이 왔었습니다. 이
차이가 원인을 정확히 가리켰습니다.

**원인**: v4.9~v4.12에서 쓰던 방식은 감시 프로세스 하나가
`[Console]::In.Peek()`로 stdin을 논블로킹으로 확인하면서 SET/TOOL/TEST
명령까지 같이 처리했습니다. **이 방식이 파이프로 연결된(리다이렉트된)
stdin에서는 신뢰할 수 없다는 게 실제로 확인됐습니다** — 이건 잘 알려진
PowerShell/.NET의 함정입니다. 맨 처음 보낸 명령은 어쩌다 타이밍이
맞아서 잡혔지만, 그 이후로 보낸 명령들은 `Peek()`이 계속 "데이터
없음"으로 잘못 판단해서 전부 유실됐던 것입니다.

**수정**: 읽기와 쓰기를 다시 분리했습니다.
- **감시(폴링) 프로세스**: stdin을 아예 안 씁니다. Photoshop 전경색을
  주기적으로 읽어서 stdout으로만 보고하는 순수 단방향 프로세스로
  단순화했습니다.
- **SET/TOOL/TEST 명령**: 각각 독립적인 짧은 프로세스를 새로 띄워서
  실행합니다(`execFile`, 8초 타임아웃). 감시 프로세스와 완전히 분리돼
  있어서 stdin 경합/유실 문제 자체가 생길 수 없습니다. "Photoshop을
  끄면 계속 다시 켜짐" 버그를 막기 위한 `Get-Process` 사전 확인은 모든
  명령 스크립트 공통 헬�퍼(`PS_HELPERS`)로 유지했습니다.

**검증**: 독립 프로세스 방식을 흉내 낸 테스트에서, 연속으로 4번 명령을
보내도(실제 로그에서 SET이 4번 실패했던 것과 같은 상황) **4번 다 정상
응답이 오는 것**을 확인했습니다 — 이전 stdin 방식이었다면 첫 번째만
성공하고 나머지는 유실됐을 상황입니다.

## v4.12 변경사항 — "F11도 팔레트 선택도 로그에 없다"는 지적 — 로그 커버리지 자체가 부족했음

아니라 그냥 "기록하는 코드가 없었다"는 뜻이었습니다. 이번엔 파이프라인의
**모든 단계**에 로그를 심어서, 정확히 어디서 끊기는지 다음 로그
한 번으로 확정할 수 있게 했습니다.

### 추가한 로그 지점 (순서대로)

1. `[overlay-popup] 필드 pointerdown 수신` — 팝업 안 필드를 클릭하는
   순간 렌더러가 그 클릭을 받는지
2. `[overlay-popup] 필드 드래그 커밋: rgb(...)` — 마우스를 뗄 때 실제로
   커밋 로직이 실행되는지
3. `[overlay] 팔레트에서 색 선택 수신: r=.. g=.. b=..` — main 프로세스가

4. `[overlay] sendToUxp(setColor) 호출됨. WS 연결됨=true/false` — 실제

5. `[com-bridge] 명령 전송: SET r,g,b` — COM 브릿지 프로세스의 stdin까지
   명령이 실제로 전달되는지
6. `SET_OK`/`SET_ERR` — PowerShell이 그 명령을 실행한 결과

그리고 F11 쪽도:
- `[overlay] F11(팝업 표시 키) 눌림 감지. 현재 popupVisible: ...` —

- `[overlay] Photoshop이 활성 앱이 아니라서 팝업을 열지 않음` — 만약
  안 열렸다면 이게 원인인지
- `[overlay] 팝업 열림` / `[overlay] 팝업 닫힘`

이전과 똑같이: SHA Paint 켜고 → F11로 팝업 열고 → 필드에서 색 하나
고르고 손 떼고 → 로그 파일 확인. 이번엔 위 6단계 로그가 어디까지
찍히고 어디서 멈추는지 그대로 보내주시면, 정확히 그 지점의 코드를
고칠 수 있습니다.

진단 테스트 결과가 `TEST_OK APPNAME: VERSION: COLOR:0,0,0`이었습니다 —
**이름과 버전이 빈 문자열, 색은 검정.** 이건 단순한 명령어 오타 수준의
문제가 아니라, **COM이 사용자가 보고 있는 실제 Photoshop 창이 아닌
다른(화면에 안 보이거나 아직 초기화 안 끝난) 인스턴스에 연결되고
있다는 강한 증거**입니다. 잘못된 값이었다면 조용히 빈 문자열이 아니라
명확한 예외가 났을 겁니다.

**판단**: 이건 스크립트를 더 다듬는다고 확실히 고쳐질 문제가 아닐 수
있습니다. COM 브릿지 코드는 남겨뒀지만(작동하면 보너스), **지금부턴
UXP 패널 + WebSocket 경로를 주력으로 권장**합니다 — 이전에 안내드린
"워크스페이스에 패널 열린 상태 저장" 방법을 쓰면 매번 수동으로 열
필요 없이 사실상 자동으로 연결됩니다.

### ⚠️ 위험한 버그 발견 및 수정: 오탐으로 SHA Paint가 스스로 꺼짐

로그를 보니, 첫 실행에서 `PS_NOT_RUNNING`이 딱 **1번** 감지되자마자
**3초 만에 SHA Paint가 통째로 종료**됐습니다. Photoshop이 실제로 켜져
있었을 가능성이 있는데도 단 1번의 오탐으로 앱이 꺼져버린 것입니다.

**수정**:
1. PowerShell의 Photoshop 프로세스 감지를 `Get-Process -Name
   "Photoshop"`(정확히 일치해야 함) 대신 **와일드카드 매칭**
   (`*Photoshop*`)으로 완화했습니다 — 실제 프로세스 이름이 "Photoshop
   2026"처럼 버전 접미사가 붙어있으면 정확 일치가 오탐의 원인이 될 수
   있습니다.
2. "Photoshop이 감지 안 됨" 신호를 **1번 받고 바로 종료하던 것을,
   연속 8번(약 2.4초) 이상 받아야만** 실제로 종료하도록 디바운스를
   추가했습니다. 색 변경이 감지되면(=Photoshop이 살아있다는 증거)
   카운트가 즉시 리셋됩니다.

**검증**: 로그에서 실제로 벌어진 것과 같은 "1회 오탐" 상황을
재현했을 때 종료가 안 되는 것, 곧이어 정상 신호가 오면 카운트가
리셋되는 것, 진짜로 연속 8회 실패해야만 종료되는 것을 확인했습니다.

### 앞으로의 방향 제안

COM 브릿지를 계속 파고들고 싶으시면, **작업관리자에서 Photoshop이
정확히 어떤 이름으로 표시되는지** 알려주시면 추가로 좁혀볼 수 있습니다.
다만 지금 증거(이름/버전이 빈 문자열)로는 단순 이름 불일치보다 더 근본적인
문제일 가능성이 있어 보이니, **당장 급하시면 UXP 패널 경로(워크스페이스
저장 방법 포함)를 주력으로 쓰시길 권합니다.**

## v4.9 변경사항 — Action Manager 방식으로 전환 + 파일 로깅 (핵심 원인 후보 발견)

### 핵심 발견: Adobe 공식 포럼의 알려진 버그

Adobe Creative Cloud Developer Forums에 정확히 일치하는 보고가 있습니다:
*"app.foregroundColor를 읽는 건 되는데, 문서에는 read+write라고 나와있어도
실제로 설정(set)은 안 된다"* — 최신 Photoshop 버전에서 **직접 프로퍼티
대입 방식(`app.foregroundColor = 새색`)이 신뢰할 수 없다는 것**이
Adobe 자체 개발자 커뮤니티에서도 보고된 문제입니다.

우리 COM 브릿지는 지금까지 정확히 이 방식(`$app.ForegroundColor = $color`)을
썼습니다. 반면 **UXP 플러그인은 처음부터 Action Manager(`batchPlay`)
방식을 썼고 실제로 성공했습니다** — 이게 COM 브릿지와 UXP 플러그인의
동작 차이를 설명하는 유력한 원인일 수 있습니다.

**수정**: COM 브릿지의 `setForegroundColor`/`activateTool`을 직접
프로퍼티 대입 대신 **Action Manager(`ExecuteAction` + `ActionDescriptor`/
`ActionReference`)** 방식으로 전면 재작성했습니다. 이건 우리 UXP
플러그인의 `batchPlay({_obj:"set", _target:[{_ref:"color",
_property:"foregroundColor"}], to:{_obj:"RGBColor",...}})`와 정확히
같은 메커니즘을, COM에서 쓸 수 있는 형태(`StringIDToTypeID`,
`PutProperty`, `PutObject`, `ExecuteAction`)로 옮긴 것입니다.

**⚠️ 여전히 검증 안 됨**: 이 Action Manager COM 코드는 손으로 직접
작성했고 실제 Photoshop에서 테스트하지 못했습니다. `StringIDToTypeID`에
넘기는 문자열(`"set"`, `"color"`, `"foregroundColor"`, `"RGBColor"`,
`"red"`/`"green"`/`"blue"`, `"select"`, 도구 이름)이 정확한지가 관건인데,
이 문자열들은 UXP의 batchPlay JSON에서 이미 검증된 것과 동일한 값들을
그대로 가져다 썼습니다.

### 로그를 파일로도 저장 (진단 편의성)

터미널을 매번 찾기 번거로우실 수 있어서, 모든 콘솔 로그를
**`sh-paint-log.txt` 파일에도 동시에 기록**하도록 했습니다. 트레이 메뉴에
**"로그 파일 열기..."**를 추가해서 클릭 한 번으로 바로 열립니다. 문제가
생기면 이 파일 내용을 그대로 복사해서 보내주시면 됩니다.

**검증한 것**: 파일 로깅 로직 자체(콘솔 출력이 타임스탬프와 함께 파일에
정확히 기록되는 것)를 Node.js로 직접 확인했습니다. Action Manager COM
코드 자체는 이 환경에 Photoshop이 없어 검증 불가능합니다 — 실제로
돌려보시고 트레이의 "Photoshop 연결 테스트"를 눌러서 결과를(성공이든
실패든) 로그 파일에서 확인해서 알려주세요.

## v4.8 변경사항 — "Photoshop이 계속 다시 켜짐" 버그 수정 (심각) + 아키텍처 재설계

### ⚠️ 심각한 버그: Photoshop을 꺼도 계속 다시 켜지던 문제

**원인**: Windows COM은 `New-Object -ComObject Photoshop.Application`을
호출할 때, **Photoshop이 지금 안 떠있으면 자동으로 실행시켜버립니다**
(COM의 표준 동작 — "이 앱이 필요한데 없으니 켜줄게"). 그런데 예전
버전은 감시(watcher) 프로세스가 **300~400ms마다 이 호출을 반복**했습니다.
사용자가 Photoshop을 끄면, 0.4초 안에 감시 프로세스가 또 이 COM 호출을
시도하고, Windows가 "없으니 켜준다"며 Photoshop을 다시 실행 — 이게
끝없이 반복된 것입니다.

**수정**: 이제 **모든 COM 호출 전에 반드시 `Get-Process`로 Photoshop
프로세스가 실제로 떠있는지 먼저 확인**하고, 없으면 COM 호출 자체를
아예 하지 않습니다. 이걸로 자동 재실행 루프가 원천 차단됩니다.

### "최초 실행에선 브러시 적용 안 되다가 팝업 껐다 켜면 됨" — 아키텍처로 개선

**사용자가 발견한 패턴**: 정확한 단서였습니다. 예전 구조는
`setForegroundColor`/`activateTool`을 부를 때마다 **매번 새 PowerShell
프로세스를 띄우고 그 안에서 새 COM 객체를 만들었습니다.** 이 "콜드
스타트"(PowerShell 시작 + COM 최초 연결)가 첫 호출에서 유독 오래
걸리거나, 동시에 돌고 있던 별도의 감시 프로세스와 COM 연결을 두고
경합했을 가능성이 있습니다.

**수정**: 감시 프로세스 하나만 계속 띄워두고, 그 안에서 COM
객체(`$app`)를 **한 번만 만들어 재사용**합니다. 색 설정/도구 전환
명령도 이제 새 프로세스를 안 띄우고 **같은 프로세스의 stdin으로
전달**해서 처리합니다 — 매번 새로 연결하지 않으니 첫 호출도 이미
"워밍업된" 연결을 씁니다.

### 새 프로토콜 (stdin/stdout 한 줄 = 한 메시지)

- Node → PowerShell: `SET r,g,b` / `TOOL name` / `TEST`
- PowerShell → Node: `COLOR r,g,b`(색 변경 감지) / `SET_OK`·`SET_ERR ...` /
  `TOOL_OK`·`TOOL_ERR ...` / `TEST_OK ...`·`TEST_ERR ...` /
  `PS_NOT_RUNNING`(Photoshop 없어서 명령 무시함) / `PS_GONE`(감시 중
  Photoshop이 사라짐을 감지)

### Photoshop 종료 시 SHA Paint도 함께 종료

**추가**: `PS_GONE` 신호를 받으면(Photoshop 프로세스가 더 이상
감지되지 않으면) 팝업을 닫고 **SHA Paint 앱 자체도 `app.quit()`으로
종료**합니다.

### 검증한 것

- 프로토콜 파싱: `COLOR 10,20,30` → `SET_OK` → `PS_GONE` → `COLOR
  99,88,77` 순서의 메시지 스트림을 흘려보내서, 색상 보고 2건이 정확히
  구분되고 `SET_OK` 같은 무관한 줄이 색상으로 오인되지 않는 것, `PS_GONE`
  콜백이 정확히 호출되는 것을 확인
- 명령 전송: Node가 자식 프로세스의 stdin에 쓴 `SET`/`TOOL`/`TEST`
  3개 명령이 그대로(순서·내용 손실 없이) 전달되는 것을 실제 자식
  프로세스로 확인

### 여전히 검증 못한 것

`Get-Process -Name "Photoshop"`이 사용자의 실제 Photoshop 실행 파일
이름과 정확히 일치하는지(버전에 따라 "Photoshop", "Photoshop 2026" 등
프로세스 이름이 다를 수 있음)는 실제 환경에서 확인이 필요합니다. 만약
`PS_GONE`이 Photoshop이 켜져 있는데도 뜬다면(오탐), 이 프로세스 이름
불일치가 원인일 가능성이 큽니다 — 그 경우 실제 작업관리자에 뜨는
Photoshop 프로세스 이름을 알려주시면 바로 맞추겠습니다.

## v4.7 변경사항 — COM 브릿지 진단 도구 추가 (정확한 원인 확인용)

**보고된 증상**: Photoshop을 먼저 켜고 SHA Paint를 실행하면, 팔레트에서
고른 색이 브러시에 적용 안 되고 스포이드 추출도 팔레트에 반영 안 됨.
**꼭 UXP 플러그인(Luminance Picker) 패널을 최초 1회 열어야만** 연동이
된다는 보고.

**솔직한 판단**: 이건 사실 **COM 브릿지가 실제로는 전혀 동작을 안 하고
있고, 지금까지 "된다"고 느끼신 건 예전부터 있던 UXP 패널↔WebSocket
경로가 작동한 것일 가능성이 높습니다** — 패널을 열어야만 된다는 보고가
정확히 그 증거입니다(WebSocket 경로는 원래 패널이 열려야만 연결됨).
COM 브릿지는 코드상으로는 패널과 무관하게 동작해야 하는데, 왜 실제로
동작을 안 하는지는 로그 없이는 알 수 없어서, 이번엔 진단 도구부터
넣었습니다.

**추가한 것**:
- `setForegroundColor`/`activateTool` 호출 시 **성공/실패 모두** 콘솔에
  기록 (이전엔 실패만 기록해서, 애초에 시도됐는지조차 알 수 없었음)
- `comBridge.testConnection()` — Photoshop 앱 이름/버전/현재 전경색을
  읽어와서 콘솔에 출력하는 진단 함수. **트레이 메뉴에 "Photoshop 연결
  테스트 (콘솔 확인)"** 항목으로 언제든 수동 실행 가능
- **앱을 켜면 1.5초 뒤 자동으로 이 진단을 1회 실행**해서, 아무것도 안
  눌러도 바로 콘솔에서 COM 연결 상태를 확인할 수 있음

### 확인 부탁드리는 절차

1. Photoshop을 켠다
2. SHA Paint를 실행한다 (**UXP 패널은 열지 않은 채로**)
3. 오버레이 앱 터미널에서 `[com-bridge] === 진단 테스트 성공/실패 ===`
   로그를 확인한다
4. 성공이면 뒤에 찍히는 `APPNAME:`, `VERSION:`, `COLOR:` 값도 함께
   알려주시고, 실패면 그 에러 메시지 전체를 그대로 알려주세요

이 로그 하나로 COM 브릿지가 정말 문제인지, 아니면 다른 이유인지 확실히
가릴 수 있습니다. "명도 그래프를 먼저 움직여야 팔레트 선택이 브러시에
반영된다"는 두 번째 증상도, 같은 원인(COM 연결이 초기엔 불안정하다가
시간이 좀 지나야 안정화되는 것)일 가능성이 있어 보이는데, 이것도 위
로그로 함께 확인해보겠습니다.

## v4.6 변경사항 — 긴/빠른 브러시 스트로크에서도 검정 오독 완전 차단

**사용자 확인**: "느리게 브러시 클릭을 하면 괜찮은데 빠르게 하거나
길게 쭉 하면 검은색으로 된다" — v4.5의 "연속 2번 확인" 방식은 Photoshop이
**짧게** 바쁠 때는 걸러지지만, 길거나 빠르게 이어지는 스트로크처럼
Photoshop이 **계속** 바쁜 상태에서는 같은 오독(검정)이 두 번 연속
나올 수 있어서 못 막았습니다.

**근본 수정**: COM 폴링 결과를 main 프로세스에서 받는 지점에
`mouseButtonDown`(좌클릭을 누르고 있는 동안, 즉 브러시 스트로크가
진행 중인지) 게이트를 추가했습니다 — **스트로크가 진행 중인 동안 들어오는
색 변경 보고는 통째로 무시**합니다. 스트로크 중엔 애초에 스포이드로 색을
뽑을 수도 없으니(마우스가 이미 눌려있는 상태라) 이 시간 동안의 보고를
전부 무시해도 안전합니다. 마우스를 떼는 순간(mouseup) 다음 폴링부터
정상적으로 다시 반영됩니다. v4.5의 "연속 2번 확인"은 그대로 남겨둬서
이중으로 방어합니다.

**검증**: 2초짜리 긴 스트로크 동안 검정 오독이 5번 연속 들어와도
팔레트가 전혀 안 바뀌고, 스트로크가 끝난 뒤엔 원래 값이 그대로 유지되는
것을 확인했습니다. 스트로크 없이(마우스 안 누른 상태) 진짜 스포이드
변경은 정상적으로 감지되는 것도 함께 확인했습니다.

## v4.5 변경사항 — 칠하는 도중 팔레트가 잠깐 검은색으로 잘못 인식되던 버그 수정

**증상**: 클릭 추적 모드를 꺼도(v4.4), 브러시로 칠하는 동안 팔레트가
잠깐 검은색으로 바뀌었다가 브러시를 떼면 원래 색으로 돌아왔습니다.

**원인**: COM 감시(watcher)가 400ms마다 Photoshop의 전경색을 읽는데,
**브러시 스트로크를 실시간 렌더링하느라 Photoshop의 UI 스레드가 바쁠 때**
COM 호출이 예외 없이 "비어있는/기본값(검정)" 객체를 그대로 반환하는
경우가 있는 것으로 보입니다. 이 오독이 진짜 색 변경처럼 팔레트에
그대로 반영됐던 것입니다.

**수정**: 폴링 로직에 "확인 절차"를 추가했습니다 — **같은 값이 연속
2번(400ms 간격으로 800ms 동안) 읽혀야만** 진짜 변경으로 인정하고
팔레트에 반영합니다. 브러시 스트로크 도중의 일시적 오독은 다음 폴링에서
재현되지 않으므로(스트로크가 끝나면 진짜 값으로 돌아오므로) 자연스럽게
걸러지고, 진짜 스포이드 색 변경은 값이 계속 유지되니 정상적으로(약
400ms 지연만 더 걸리고) 감지됩니다.

**검증**: "정상 색 유지 중 한 번만 검정으로 오독"하는 상황과 "진짜로
스포이드로 다른 색을 찍는" 상황을 각각 시뮬레이션해서, 전자는 검정이
한 번도 팔레트에 반영되지 않고 후자는 새 색이 정상적으로 감지되는 것을
확인했습니다.

**아직 남을 수 있는 위험**: 아주 긴 브러시 스트로크(800ms 이상 지속)
중에는 이론적으로 같은 오독이 두 번 연속 나올 가능성이 완전히 배제되진
않습니다. 그래도 증상이 재현되면 확인 횟수를 3회로 늘리는 등 더 강하게
막을 수 있으니 알려주세요.

**검증**: 오탐 1회 후 바로 정상으로 돌아오는 경우 팝업이 안 숨겨지고,

다시 렌더링됩니다.

**검증**: 캔버스를 500×400으로 리사이즈했을 때, 내부 해상도가 정확히
500×400으로 갱신되는 것을 확인했습니다.

## v4.3 변경사항 — UXP 플러그인 패널 없이도 팝업만으로 완전히 동작 (Windows COM 브릿지)

**질문**: 지금은 Photoshop 안에서 Luminance Picker 패널을 열어야만
(WebSocket 연결이 이뤄지면서) 팝업이 제대로 동작하는데, 패널을 아예
열지 않고 팝업만으로 연결할 방법이 있을까?

**답**: 있습니다. Windows의 Photoshop은 설치 시 **COM(ActiveX) 자동화
인터페이스**를 자동으로 등록합니다 — VBA/VBScript 등에서 예전부터
Photoshop을 제어하던 바로 그 방식입니다. 이걸 쓰면 **UXP 플러그인이 전혀
필요 없이** 이 오버레이 앱이 PowerShell을 통해 Photoshop을 직접 제어할
수 있습니다.

새로 만든 `com-bridge.js`가 담당하는 것:
- **`setForegroundColor(r,g,b)`**: 색 확정(필드 드래그, 슬라이더, F8
  등) 시 PowerShell + COM으로 Photoshop 전경색을 직접 설정
- **`activateTool(name)`**: 스포이드/브러시 전환도 COM으로 직접
  (`app.CurrentTool` 프로퍼티 — Adobe 공식 스크립팅 가이드에 문서화된
  방식)
- **`startWatcher(callback)`**: 프로세스 하나를 계속 띄워두고 400ms마다
  전경색을 읽어서, 스포이드 등으로 바뀌면 자동으로 감지 — UXP 플러그인이
  하던 폴링을 대체

`main.js`의 `sendToUxp()`가 이제 **WebSocket(UXP 패널)과 COM 브릿지
양쪽으로 동시에** 보냅니다 — 패널이 열려있으면 그쪽도 갱신되고, COM
브릿지는 패널 상태와 무관하게 Photoshop이 켜져만 있으면 항상 동작합니다.
즉 **패널을 한 번도 안 열어도 F9/F11/F8/F10 전부 정상 동작**합니다.

### ⚠️ 검증 안 됨 — 반드시 직접 테스트 필요

이 코드는 **실제 Windows + Photoshop 환경에서 검증되지 않았습니다** (이
작업 환경엔 Windows/Photoshop 자체가 없음). Adobe 공식 문서에 나온
COM/스크립팅 API(`Photoshop.Application`, `ForegroundColor`,
`CurrentTool`)를 기반으로 최대한 정확하게 작성했지만:

- 검증한 것: stdout이 청크 단위로 쪼개져 들어와도(PowerShell 출력이
  줄 경계에서 끊겨서 도착하는 상황) 파싱 로직이 정확히 다시 합치는 것을
  Node.js로 직접 재현해서 확인
- 검증 못한 것: 실제 PowerShell + Photoshop COM 자동화 호출 자체가
  성공하는지, `Photoshop.Application`/`Photoshop.SolidColor` ProgID가
  사용자의 Photoshop 버전에서 정확히 그 이름인지, `CurrentTool`에 넣는
  문자열("eyedropperTool", "paintbrushTool")이 정확한지

실제로 실행해보시고 콘솔(오버레이 앱 터미널)에 `[com-bridge]`로 시작하는
에러가 뜨면 그 메시지를 그대로 알려주세요 — 바로 고치겠습니다. UXP
플러그인/패널 쪽은 그대로 두었으니, COM 브릿지가 잘 안 되더라도 예전처럼
패널을 열어서 쓰는 방법은 계속 유효합니다.

## v4.2 변경사항 — 클릭 추적 모드 기본 ON, Photoshop 비활성 시 팝업 자동 숨김

### 1. 클릭 추적 모드가 이제 기본값

**이전**: F9를 눌러야 펜 촉 접촉만으로 팝업이 열렸습니다.

**지금**: 앱을 켜면 **처음부터 클릭 추적 모드가 켜진 상태**입니다 —
F9를 누르지 않아도 바로 펜 촉을 대면 팝업이 뜹니다. F9를 누르면 끄고
(F11 hold 방식으로 전환), 다시 누르면 켤 수 있는 건 그대로입니다.

### 2. Photoshop을 끄거나 최소화하면 팝업도 함께 사라짐

**추가**: 팝업이 열려있는 동안 400ms마다 지금 Photoshop이 여전히
활성(포커스) 앱인지 확인합니다. Photoshop을 **최소화**하거나, **다른
앱으로 전환**하거나, **아예 종료**하면 — 이 셋 다 공통적으로 "더 이상

팝업은 포커스를 뺏지 않는 창(`focusable:false`)이라, 사용자가 팝업 안에서
필드를 드래그하며 색을 고르는 동안에는 Photoshop이 계속 활성 상태로
유지됩니다 — 그래서 이 감시 로직이 색을 고르는 도중 실수로 팝업을
닫아버리는 일은 없습니다.

**검증**: ① 기본 상태(F9 안 누름)에서 클릭 추적 모드가 켜져 있는 것,
F9 두 번으로 껐다 켜지는 것, ② Photoshop이 활성일 땐 팝업이 유지되고
비활성이 되는 순간 자동으로 숨겨지는 것을 순수 로직으로 확인했습니다.

## v4.1 변경사항 — "Cannot find native binding" 실행 오류 수정 + 이름을 "SHA Paint"로 변경

**문제**: v4.0에서 만든 설치파일을 실제로 실행하면
`Error: Cannot find native binding. npm has a bug related to optional
dependencies`라는 오류가 났습니다.

**원인 1 — 크로스 플랫폼 npm install 문제**: 이 설치파일을 만든 빌드
환경이 리눅스 샌드박스였는데, `npm install`을 그냥 실행하면 npm은
**지금 실행 중인 OS(리눅스)에 맞는 네이티브 바이너리만** 받아옵니다.
`@miniben90/x-win`, `@nut-tree-fork/nut-js` 같은 패키지는 플랫폼별로
별도 npm 패키지(`x-win-win32-x64-msvc`, `libnut-win32` 등)로 배포되는데,
Windows용 패키지가 아예 설치 안 된 채로 Windows용 설치파일에 패키징된
것입니다.

**수정**: `npm install --os=win32 --cpu=x64 --include=optional`로 호스트
OS와 무관하게 Windows용 네이티브 바이너리를 명시적으로 강제 설치하도록
바꿨습니다. 실제로 `x-win-win32-x64-msvc`, `libnut-win32`,
`uiohook-napi`의 `win32-x64` 바이너리가 전부 받아지는 것을 확인했습니다.

**원인 2 — asar 안에 바이너리가 갇힘**: 네이티브 `.node` 파일은 Electron의
asar 압축 아카이브 안에서는 직접 로드할 수 없고 "unpack" 처리가 돼야
하는데, `uiohook-napi`의 바이너리는 `prebuilds/<platform>/*.node`처럼
중첩된 경로에 있어서 electron-builder의 기본 자동 감지 로직이 못
잡아냈습니다 (`@nut-tree-fork`, `@miniben90`는 정상적으로 unpack됐지만
`uiohook-napi`만 asar 안에 갇혀 있었음).

**수정**: `package.json`의 `build.asarUnpack`에 `"**/*.node"`를 명시해서
경로 깊이와 무관하게 모든 네이티브 바이너리가 확실히 asar 밖으로
언패킹되도록 했습니다. 재빌드 후 세 모듈(`uiohook-napi`,
`@nut-tree-fork/libnut-win32`, `@miniben90/x-win-win32-x64-msvc`)의
`win32-x64` 바이너리가 전부 `app.asar.unpacked` 안에 실제로 존재하는
파일로 확인했습니다 (`asar list`로 내부 구조까지 직접 검증).

**프로그램 이름**: `Luminance Overlay` → **`SHA Paint`**로 변경했습니다
(트레이 툴팁, 설정 창 제목, `productName`, 설치파일명 `SHPaintSetup-*.exe`
전부 반영).

## v4.0 변경사항 — 설치파일 하나로 패키징 (npm/node 몰라도 되게)

지금까지는 매번 `npm install` / `npm start`로 실행해야 했는데, 이제
**설치파일(.exe) 하나로** 다음을 전부 자동화했습니다:

1. Electron/Node.js 런타임이 설치파일 안에 통째로 들어있어서, 설치 후엔
   npm이나 Node.js가 따로 없어도 그냥 실행됩니다.
2. **최초 실행 시 자동으로** 번들된 Photoshop 플러그인(`.ccx`)을 열어서
   Creative Cloud Desktop의 설치 창을 띄웁니다. 사용자는 그 창에서
   "Install locally"만 한 번 누르면 됩니다 (완전 무음 설치는 아니지만,
   `.ccx` 파일을 직접 찾아 더블클릭하는 수고는 사라짐).
3. 트레이 메뉴에 **"Photoshop 플러그인 설치..."** 항목을 추가해서, 나중에
   플러그인을 업데이트하거나 재설치할 때 언제든 다시 트리거할 수 있습니다.

### 설치파일 만드는 법 (한 번만, Windows 컴퓨터에서 직접)

```cmd
cd luminance-overlay-app
npm install
npm run dist
```

`dist\LuminanceOverlaySetup-1.0.0.exe`가 만들어집니다. **이 파일 하나만
배포/공유하면 됩니다** — 그 이후로는 이 `.exe`를 실행하는 사람은 npm/node를
전혀 몰라도 됩니다.

### 이 환경에서 확인한 것 / 확인 못한 것

이 작업환경(디스플레이 없는 리눅스 샌드박스)에서 실제로 `npx electron-builder
--win --x64`를 실행해서 검증했습니다:
- ✅ Electron 바이너리 다운로드, 앱 패키징까지 정상 진행됨
- ✅ 아이콘(256×256 포함 멀티사이즈 `.ico`) 문제를 발견하고 수정함
- ✅ `extraResources`로 `.ccx`가 포함되는 설정, `author` 필드 누락 경고까지
  전부 확인하고 고침
- ⨯ **최종 `.exe` 서명 단계에서 막힘** — 이건 **리눅스에서 Windows 빌드를
  할 때만 필요한 `wine`이 없어서**입니다. 실제 Windows 컴퓨터에서
  `npm run dist`를 실행하면 이 단계 자체가 필요 없는(네이티브로 처리되는)
  과정이라 문제없이 완료돼야 합니다.

즉 **설정 자체는 이 지점까지 검증됐고**, 실제 `.exe` 생성과 "최초 실행 시
자동으로 CCD 설치 창이 뜨는지"는 Windows 환경에서 직접 확인이 필요합니다.
안 되는 부분 있으면 알려주세요.

## v3.13 변경사항 — 휠로 명도 조정 시 실시간으로 브러시 색에도 적용

**이전**: 휠로 명도 그래프를 움직이면 팝업 안에서는 보이는데, 실제
Photoshop 브러시 색(전경색)에는 반영되지 않았습니다 — 필드 드래그나
슬라이더로 직접 골라야만 적용됐습니다.

**추가**: 휠로 조정한 명도도 이제 실시간으로 브러시에 적용됩니다.
- 팝업 안 시각적 갱신(필드/그래프)은 그대로 빠르게(~16ms, 60fps)
- 실제 Photoshop 전경색 적용은 90ms 디바운스를 걸었습니다 — 휠 한 칸마다
  매번 커밋하면 빠르게 굴릴 때 Undo 히스토리가 스팸처럼 쌓이기 때문에,
  짧게 멈출 때마다(또는 다 굴리고 멈췄을 때) 마지막 값만 한 번 반영합니다.
  체감상 "실시간"이면서 히스토리는 깨끗하게 유지됩니다.

**검증**: 10ms 간격으로 5번 연속 휠 조작(서로 다른 명도값)을 시뮬레이션했을
때, 실제 커밋은 정확히 1번만 발생하고 그 값도 마지막(최종) 명도인 것을
확인했습니다.

## v3.12 변경사항 — 도움말이 항상 UI를 가리던 버그, 임시로 도움말 제거

**원인 발견**: `.help-overlay` CSS 규칙에 `display: flex`를 직접 넣었는데,
이게 `hidden` HTML 속성의 기본 동작(`[hidden] { display: none }`)과
**우선순위(specificity)가 정확히 같아서**, 나중에 선언된 제 규칙이 이겨
`hidden`이 지정돼 있어도 **도움말이 항상 화면 전체(z-index:10)를 덮고
있었습니다.** 반투명한 어두운 배경이라 눈에 잘 안 띄었을 뿐, 필드
드래그나 슬라이더 클릭이 전부 이 오버레이에 막혀서 밑에 있는 실제
UI로는 전달되지 않고 있었습니다 — "팔레트에서 색을 골라도 브러시에
반영 안 됨" 현상의 실제 원인이 이것이었을 가능성이 큽니다.

**조치**: 요청하신 대로 도움말 버튼/오버레이를 **통째로 제거**했습니다
(`overlay.html`/`overlay.css`/`overlay.js` 전부에서 관련 코드 삭제).
나중에 다시 추가할 때는 `hidden` 대신 JS로 직접 `display` 스타일을
제어하거나, CSS를 `.help-overlay:not([hidden])`처럼 작성해서 이 우선순위
문제가 재발하지 않게 하겠습니다.

**재검증**: 도움말 관련 엘리먼트가 DOM에 전혀 없는 것, 필드 드래그 후
`pickColor`가 정상 호출되는 것(색상 `{r:166,g:95,b:151}`), 외부(스포이드)
색 변경을 시뮬레이션했을 때 스와치가 실제로 새 색(`rgb(157,180,107)`)으로
갱신되는 것을 확인했습니다.

## v3.10 변경사항 — "고른 색이 브러시에 자동 반영 안 됨" 버그 수정

**원인 추정**: 팝업의 색상 필드(비정형 블롭)가 작다 보니, 드래그로 색을
고르는 도중 커서가 캔버스 경계를 살짝만 벗어나도 `pointerleave`가 먼저
발동해서 내부 `dragging` 플래그가 `false`가 됩니다. 그 뒤 실제로 마우스
버튼을 뗄 때(`pointerup`)는 커서가 이미 캔버스 밖에 있어서 이 이벤트가
캔버스로 아예 전달되지 않거나, 전달돼도 `dragging`이 이미 꺼져있어서
"색 확정"(`pickColor` 호출 → 브러시 색 적용) 로직 자체가 실행되지
않았습니다.

**수정**: `pointerdown` 시점에 `setPointerCapture`를 걸었습니다. 이러면
커서가 캔버스 경계를 벗어나도 이후의 `pointermove`/`pointerup` 이벤트가
계속 그 캔버스로 전달되어, 어디서 손을 떼든 정상적으로 색이 확정되고
브러시에 반영됩니다. 캡처가 지원되지 않는 구형 환경을 위해, 캡처가 실패한
경우에만 예전처럼 `pointerleave`에서 드래그를 취소하는 폴백도 남겨뒀습니다.

**검증**: 드래그 도중 캔버스 밖으로 나갔다가(`pointerleave` 발생) 캔버스
밖에서 손을 떼는 상황을 재현했을 때, 포인터 캡처 덕분에 `pickColor`가
정상적으로 호출되는 것을 확인했습니다.

## v3.9 변경사항 — 6가지 요청 반영

### 1. Esc로도 팝업 닫기

F11 토글에 더해 Esc 키로도 언제든 닫을 수 있습니다.

### 2. 명도 그래프가 "그 색상의" 범위만 표시

**이전**: 명도 슬라이더가 항상 검정(0%)~흰색(100%)의 고정 그라데이션이었습니다.

**지금**: `colorMath.js`에 `findLightnessRangeForChroma(hueDeg, chroma)`를
추가했습니다 — 어떤 hue에서 "L*별 최대 chroma"는 L*=0/100 근처에서 0에
가깝고 중간 어딘가(피크)에서 최댓값을 갖는 단봉(unimodal) 형태인데, 지금
채도를 그대로 유지한 채 표현 가능한 L* 구간 `[Lmin, Lmax]`를 이 형태에서
찾아냅니다. 명도 트랙은 이제 검정/흰색이 아니라 **그 구간 안에서 실제로
나타나는 색들의 그라데이션**을 그리고, 슬라이더도 그 구간 안에서만
움직입니다. 채도가 높을수록(스펙트럼이 좁을수록) 그래프도 좁아지고,
채도가 낮을수록 넓어집니다 — 극단으로 밀어도 검은색/흰색으로 새지 않고
그 색 고유의 한계에서 멈춥니다.

**검증**: 채도 60짜리 빨간 계열 색을 극단적으로 계속 밝게/어둡게
조정했을 때, 0이나 100이 아니라 정확히 `Lmax`(67.7)/`Lmin`(24.2)에서
멈추고 색상(hue)은 완전히 그대로 유지되는 것을 확인했습니다.

### 3. 휠 조작 끊김(랙) 최적화

원인은 휠 이벤트마다 팝업 전체(220×180픽셀)를 다시 그리는 무거운
렌더링을 매번 트리거했던 것입니다. 이제 짧은 시간(~16ms, 약 60fps)
안에 들어온 여러 휠 이벤트를 모아뒀다가 **실제 재렌더링은 한 번만**
하도록 스로틀링했습니다. 값 조정 자체(`adjustLightness`)는 매 이벤트마다
즉시 반영되어 반응성은 그대로입니다. 10회 연속 휠 이벤트 → 실제 렌더
호출 1회로 검증했습니다.

### 4. F12 스포이드↔브러시 전환 기능 제거

`main.js`, `config.js`, 설정 패널에서 관련 코드를 전부 제거했습니다.
팝업 상단의 스포이드 아이콘 버튼(클릭으로 스포이드 전환)은 F12와
무관한 별개 기능이라 그대로 남아있습니다.

### 5. 전체 색역 모드에서 자유롭게 선택 가능하게

**원인**: "전체 색역 보기"를 켜서 필드가 시각적으로는 꽉 차게 그려져도,
드래그해서 색을 고르는 로직(`clampChromaToGamut()`)이 여전히 무조건
호출되면서 실제 선택 가능한 색은 진짜 색역 경계 안으로 되돌아가
버렸습니다 — 눈에는 넓어 보이는데 실제로 고를 수 있는 색은 "일부분
보기"와 똑같았던 것입니다.

**수정**: "전체 색역 보기"일 때는 이 클램프 호출을 아예 건너뛰어서,
필드 사각형 전체 어디든(색역 밖의 근사치 포함) 자유롭게 선택할 수
있습니다. 같은 화면 좌표를 클릭했을 때 "일부분 보기"에서는
`rgb(231,0,122)`로 색역 경계에 묶였던 것이, "전체 색역 보기"에서는
`rgb(255,0,125)`로 더 확장된 값이 선택되는 것을 확인했습니다. (전체
색역 모드에서는 명도 슬라이더도 색상 유지 범위 대신 0~100 전체로
전환되어, 완전히 자유로운 탐색이 가능합니다.)

### 6. Photoshop이 활성 앱일 때만 팝업 표시

**원인**: F11/F9가 마우스 위치와 무관하게 항상 팝업을 띄워서, Photoshop이
아닌 다른 창에서 작업 중에도 팝업이 떴습니다.

**수정**: `@miniben90/x-win` 패키지의 `activeWindow()`(동기 함수)로 지금
활성 창이 Photoshop인지 확인한 뒤에만 팝업을 **엽니다**. 이미 열려 있는
팝업을 **닫는 것**은 Photoshop이 활성 상태가 아니어도 항상 허용합니다
(닫는 동작은 막을 이유가 없으므로).

원래 검토했던 `active-win`은 저장소가 `get-windows`로 이름이 바뀌었고,
두 패키지 모두 v9.0.0의 실제 바이너리 다운로드 링크가 깨져 있어(GitHub
릴리스 자산 404, 직접 확인함) 설치 자체가 안 됩니다. 대신
`@miniben90/x-win`(Rust/napi-rs 기반, npm 표준 `optionalDependencies`
방식이라 사전 빌드 바이너리가 안정적으로 배포됨)으로 교체했고, 이
샌드박스에서 실제로 설치·로드까지 확인했습니다(호출 자체는 디스플레이가
없는 이 환경이라 에러가 나는 게 정상이며, 실제 사용자 PC에서는 정상
동작해야 합니다).

**검증**: Photoshop 비활성 상태에서 F11을 눌러도 안 열리고, 활성 상태로
바뀐 뒤에는 정상적으로 열리고 닫히는 것, 그리고 Esc로 닫은 뒤 F11을
다시 눌렀을 때도 정상적으로 재오픈되는 것을 순수 로직으로 확인했습니다.

## v3.8 변경사항 — "전체 색역 보기"가 웨지 모양만 나오던 문제 수정

**문제**: v3.7에서 만든 "전체 색역 보기"가 실제 sRGB 경계를 정확하게
따라가다 보니(clamp 없이), 밝기가 한쪽으로 치우친 색에서는 색역 경계
자체가 비대칭이라서 정사각형의 일부(가느다란 웨지/조각 모양)만 채워지고
나머지는 텅 빈 채로 남았습니다. 참고로 보내주신 스크린샷은 정사각형
전체가 항상 매끄럽게 꽉 차 있는데, 이건 색상 정확도보다 "항상 꽉 찬
사각형"을 우선하는 방식입니다.

바꿨습니다 — 색역 경계 밖의 조합이 와도 가장 가까운 표현 가능한 색으로
근사해서 반환하니, 정사각형이 절대 비지 않고 항상 꽉 찹니다("일부분
보기"는 여전히 clamp 없이 정확하게 그립니다 — 이쪽은 원래 그런 용도).

**검증**: 웨지 현상이 나던 것과 같은 극단적 밝기(L=90)에서, "일부분
보기"는 8.3%만 채워지는 게 정상인 상태 그대로 두고, "전체 색역 보기"는
**100% 빈틈없이 채워지는 것**을 확인했습니다. 재클릭 시 정확히 원래

## v3.7 변경사항 — 팝업 열기/닫기 통합, 드래그 이동, 즉시 반영 버그 수정, 전체 색역 보기

### 1+3. 팝업 열고 닫는 조건 통합 (F11 토글 + F9 펜 터치)

**이전**: F11은 누르고 있는 동안(keydown~keyup)만 표시, F9는 좌클릭을
누르고 있는 동안만 표시 — 서로 배타적인 별개 모드였습니다.

**지금**: 하나의 규칙으로 통합했습니다.
1. **F11을 누른다** → 열림 (닫혀 있었다면), **이미 열려 있으면 다시 눌러서
   닫음** (한 번 누르면 토글, 더 이상 hold 아님)
2. **F9(클릭 추적 모드)가 켜져 있을 때 펜 촉이 닿는다(좌클릭)** → 안
   열려 있으면 엶, **펜을 떼도 안 닫힘**
3. 열린 상태에서 **F11을 한 번 더 누르면** → 닫힘 (어느 방법으로
   열렸든 F11로 닫을 수 있음)

F11과 F9는 더 이상 배타적이지 않습니다 — F9(클릭 추적)를 켜둔 상태에서도
F11은 항상 정상적으로 토글됩니다. OS 키 반복(누르고 있으면 오는 중복
keydown)에도 안 깜빡이도록 가드를 넣었습니다.

**검증**: ① F11 두 번으로 열고 닫힘, ② F11을 누른 채 키 반복 4연속에도
깜빡임 없이 1회만 토글, ③ 클릭 추적 모드에서 펜 터치 후 떼도 유지되다가
F11로 닫힘, ④ 클릭 추적 모드 중에도 F11이 정상 작동 — 4가지 시나리오
모두 순수 로직으로 확인했습니다.

### 2. 스포이드로 추출한 색이 팝업에 즉시 반영 안 되던 버그 수정

**원인**: UXP 플러그인이 "전경색이 바뀌었다"고 알려주는 WebSocket
메시지(`foregroundColor`)를 받으면 내부 상태(`state.baseRgb` 등)만
갱신하고, **이미 열려 있는 팝업에는 그 사실을 알리지 않았습니다.** 그래서
팝업을 닫았다 다시 열어야만(그때 `sendPopupOpen()`이 호출되므로) 반영된
것처럼 보였습니다.

**수정**: 이 메시지를 받을 때 팝업이 열려있으면(`popupVisible`) 그 자리에서
바로 `sendPopupOpen()`을 호출해서 즉시 다시 그리도록 했습니다.

### 팝업 창 드래그 이동

`movable: false` → `true`로 바꾸고, 상단 바(⠿ 드래그해서 이동)에
`-webkit-app-region: drag`를 줘서 마우스로 클릭+드래그하면 팝업을 원하는
위치로 옮길 수 있습니다. 버튼들은 `-webkit-app-region: no-drag`로 따로
지정해서 클릭이 그대로 동작합니다.

### 4. 전체 색역 보기 버튼

팝업 상단에 새 아이콘 버튼을 추가했습니다. 누를 때마다:
- **일부분 보기(기본)**: 모든 밝기에서 똑같은 고정 범위로 필드를 그림
  (밝기가 극단적이면 실제 색역이 작아서 필드 가운데에 작게만 나타남)
- **전체 색역 보기**: 지금 밝기(L*)에서 hue 전체를 스캔해 실제로 도달
  가능한 최대 채도를 구하고, 그 범위가 캔버스에 꽉 차도록 다시 그림
  (밝기가 극단적일수록 확대되어 보임 — 좁은 색역을 최대한 크게 볼 수 있음)

다시 클릭하면 원래의 "일부분 보기"로 돌아갑니다.

**검증**: L=50/95/5에서 전체 색역 범위가 각각 116.2/100.5/43.6으로,
밝기가 극단적일수록 작아지는(=확대되는) 것을 확인했고, 실제 렌더링에서도
"일부분 보기" 6,779픽셀 → "전체 색역 보기" 8,466픽셀로 더 꽉 차게
그려지고 재클릭 시 정확히 원상복구되는 것까지 검증했습니다.

### 1. 팝업 위치 고정 버그 수정

**문제**: 색을 고른 직후 팝업이 닫혔다가, F11을 계속 누르고 있으면 OS의
키 반복(auto-repeat)으로 다음 keydown이 들어오면서 **그 순간의 새 커서

**수정**: 팝업 표시/숨김을 `updatePopupVisibility()` 하나가 전담하도록
정리했습니다. F11을 누르고 있는 동안(`holdingShowPopupKey`)엔 재위치가
일어나지 않고, 색을 고르거나(`popup-color-picked`) 스포이드 아이콘을
눌러도 더 이상 팝업을 강제로 닫지 않습니다 — **F11을 뗄 때만 닫힙니다.**
키 반복으로 오는 중복 keydown도 `if (!holdingShowPopupKey)` 가드로 무시해서
재위치가 안 일어납니다.

가시성 상태 머신(F11 hold + F9 핀 모드 조합) 로직을 순수 함수로 분리해서
검증했습니다: F11 keydown → 표시 1회, 색 선택 후에도 유지, 키 반복 무시,
F11 keyup에서만 숨김, 핀 모드는 F11과 독립적으로 표시 여부를 결정 — 전부
의도대로 동작함을 확인했습니다.

### 2. 필드를 매끄럽게 (도트맵 느낌 제거)

Photoshop UXP 패널은 `createImageData`를 지원하지 않아 `fillRect` 타일
방식으로 우회해야 했지만(각져 보이는 원인), **이 오버레이 팝업은 완전한
Chromium(Electron 렌더러)이라 `createImageData`/`putImageData`를 온전히
지원합니다.** 그래서 다시 픽셀 단위 렌더링으로 되돌렸습니다 — UXP 패널과
렌더링 방식을 통일했던 v2.2 결정을 이 부분만 되돌린 것입니다. 결과적으로
필드가 매끄러운 그라데이션으로 보입니다.

### 3. 핀 모드 (기본 F9, 1회 토글)

켜면 F11을 누르고 있지 않아도 팝업이 계속 떠 있고, **커서를 계속
따라다닙니다** (uiohook의 `mousemove` 이벤트로 추적, ~60fps로 스로틀).
다시 누르면 꺼집니다.

### 4. 색 스캔 모드 (기본 F10, 1회 토글)

켜면 커서가 가리키는 **화면의 실제 픽셀 색**을 60ms 주기로 읽어서
(`@nut-tree-fork/nut-js`의 `screen.colorAt`) 팔레트 상태를 계속
갱신합니다. 그림 위에서 펜을 움직이면 지나가는 색이 계속 팔레트에 반영되는
방식입니다.

**중요**: 스캔 모드는 어디까지나 미리보기입니다 — 스캔되는 동안 실제
Photoshop 전경색을 자동으로 "적용"하지는 않습니다 (그러면 펜을 움직이기만
해도 계속 색이 바뀌어서 오히려 방해가 됨). 실제 적용은 여전히 팝업 안
타일을 클릭하거나 필드를 드래그해서 확정해야 합니다.

**핀 모드 + 색 스캔 모드를 함께 켜면**: 팝업이 커서를 따라다니면서 동시에
그 아래 색을 실시간으로 반영합니다 — 그림 위를 훑으면 팔레트가 계속
바뀌는, 말씀하신 그 느낌입니다.

### 검증한 것 / 못한 것

**검증함**:
- `@nut-tree-fork/nut-js`가 실제로 설치되고 `screen.colorAt`/`Point`가
  정상 로드됨을 확인 (원래 패키지명 `@nut-tree/nut-js`는 npm 레지스트리에서
  404 — 커뮤니티 포크인 `@nut-tree-fork/nut-js`로 대체했습니다)
- 팝업 가시성 상태 머신(F11 hold/keyup, F9 토글, 중복 keydown 무시) 로직을
  순수 함수로 추출해서 시나리오별로 정확히 검증
- 스캔 루프의 비동기 `colorAt` 실패 시 자동으로 스캔 모드를 끄고 에러를
  콘솔에 남기는 방어 로직 확인

**검증 못함** (Electron 전체 구동이 필요해 이 샌드박스에서 불가):
- 실제 화면에서 F9/F10/F11/F12가 정확히 의도대로 동작하는지
- `screen.colorAt`이 실제 Photoshop 캔버스 위 색을 정확히 읽어오는지
  (배율/HiDPI 디스플레이에서 좌표 스케일링이 어긋날 가능성 있음 — nut.js
  자체에 관련 이슈가 보고된 적 있음)
- 핀 모드로 커서를 따라다닐 때 창 재배치가 매끄러운지(끊김 없는지)
- 두 모드를 동시에 켰을 때 실제 체감 반응 속도

실제로 써보시고 어색한 부분(특히 HiDPI 모니터에서 스캔 좌표가 어긋나는지)
있으면 알려주세요.

## v2.5 변경사항 — 진짜진짜 근본 원인: Electron 기본 preload 샌드박스

v2.4의 절대경로 수정도 소용없었던 이유가 나왔습니다: **Electron은 20버전
이후로 preload 스크립트를 기본적으로 "샌드박스" 환경에서 실행합니다.**
이 샌드박스 안에서는 `require`가 로컬 파일(`colorMath.js` 같은)을 아예
읽을 수 없습니다 — 상대경로든 절대경로든 상관없이 안 됩니다. 그래서
`preload.js`가 계속 죽었고, `window.overlayAPI`가 계속 `undefined`였던
것입니다.

**수정**: `main.js`에서 오버레이 팝업 창과 설정 창의 `webPreferences`에
`sandbox: false`를 명시했습니다. 이러면 preload 스크립트가 일반 Node.js
`require`를 온전히 쓸 수 있게 됩니다 (`contextIsolation: true`는 그대로
유지해서, 웹페이지 쪽에는 여전히 Node API가 노출되지 않습니다 — 이건
preload 스크립트 자체의 실행 환경만 바꾸는 것입니다).

추가로 `preload.js`가 성공하면 `[preload] colorMath 로드 성공: {...}`
로그가 뜨도록 확인 로그를 추가해서, 다음부터는 이 단계가 성공했는지
실패했는지 터미널에서 바로 확인할 수 있습니다.

## v2.4 변경사항 — 진짜 근본 원인: preload.js가 아예 로드 실패하고 있었음

터미널 로그 덕분에 정확한 원인을 찾았습니다:

```
Unable to load preload script: ...preload.js
Error: module not found: ./colorMath.js
```

**Electron의 샌드박스 preload 환경(`node:electron/js2c/sandbox_bundle`을
통해 로드됨)에서는 상대경로(`./colorMath.js`) `require`가 제대로 해석되지
않았습니다.** 그래서 `preload.js` 자체가 로드 도중 죽었고, 그 결과
`contextBridge.exposeInMainWorld("overlayAPI", ...)`가 실행된 적이
없어서 `window.overlayAPI`가 아예 `undefined`였습니다. 이후 `overlay.js`의
모든 `window.overlayAPI.xxx` 호출이 "Cannot read properties of undefined"로
전부 실패한 것 — v2.3까지 고친 "L이 NaN일 때" 대응 로직은 이 문제 앞에서는
아예 실행조차 안 됐던 것입니다 (그 이전 단계에서 이미 다 죽어있었으므로).

**수정**: `preload.js`에서 `require("./colorMath.js")` 대신
`require(path.join(__dirname, "colorMath.js"))`로 절대경로를 사용하도록
바꿨습니다.

이건 실제 Windows/Electron 환경의 콘솔 로그를 보고 나서야 잡을 수 있었던
문제입니다 — v2.3에서 추가한 "팝업 창 콘솔을 npm start 터미널로 전달"하는
기능이 정확히 의도한 대로 작동해서 원인을 찾을 수 있었습니다.

## v2.3 변경사항 — "회색만 뜨고 아무 색도 안 나옴" (에러도 없이 조용히 실패)

v2.2까지 고친 뒤에도 팝업이 그냥 회색으로만 뜨는 문제가 남아있었습니다.
원인을 추적하다가 중요한 사실을 발견했습니다: **`labFieldPixel(L, a, b)`에
`L`이 `NaN`이나 `undefined`로 들어가면, 에러를 던지지 않고 그냥 조용히
`null`을 반환합니다.** 그러면 필드의 모든 타일이 "색역 밖"으로 판정돼서
아무것도 안 그려지고, 콘솔에도 에러가 안 남아서 원인을 알 방법이 없었던
것입니다 (기존에 추가한 에러 배너/로그는 "예외가 던져지는" 경우만 잡을 수
있었고, 이런 "조용한 실패"는 못 잡았음).

**수정**:
1. `overlay.js`의 `renderField()`와 `main.js`의 `showPopup()` 양쪽에서
   `state.L`(또는 `Y`)이 유효한 숫자인지 명시적으로 검사합니다.
2. 유효하지 않으면 **콘솔에 명확한 경고**(`state.L이 유효하지 않음: ...`)를
   남기고, 안전한 기본값(L=50 또는 Y=0.2)으로 대체해서 최소한 필드는
   정상적으로 그려지게 합니다.
3. `main.js`에서 팝업 창(렌더러)의 콘솔 메시지를 `npm start`를 실행한
   **터미널로 그대로 전달**하도록 했습니다 (`console-message` 이벤트).
   이 팝업 창은 `frame:false`라 우클릭으로 개발자 도구를 열기 번거로운데,
   이제 터미널만 봐도 렌더러 쪽 에러/경고가 다 보입니다.

**검증**: `L=NaN`으로 강제 시뮬레이션했을 때 경고 로그가 정확히 찍히고,
그럼에도 50으로 대체되어 필드에 750가지 이상의 서로 다른 색 조합이
정상적으로 그려지는 것을 확인했습니다.

혹시 아직도 회색만 뜬다면, 이제 `npm start`를 실행한 터미널에
`[overlay-popup]` 또는 `[overlay]`로 시작하는 로그가 찍힐 겁니다 —
그 내용을 그대로 알려주시면 바로 원인을 잡을 수 있습니다.

## v2.2 변경사항 — Photoshop 패널과 완전히 동일한 렌더링 로직으로 통일

Photoshop 플러그인 쪽에서 `createImageData`/`putImageData`가 UXP에서 지원
안 된다는 걸 발견하고 `fillRect` 타일 방식으로 바꿨는데(플러그인 README
v1.9.0 참고), 이 오버레이 앱의 팝업도 원래 `createImageData`를 쓰고
있었습니다. Electron은 완전한 Chromium이라 이 API 자체는 지원되지만,
두 UI가 항상 정확히 같은 방식으로 그려지도록 이쪽도 동일한 `fillRect`
타일 로직으로 통일했습니다. `colorMath.js` 사본도 다시 동기화했습니다
(이전에도 한 번 두 프로젝트 사본이 어긋난 적이 있어서, 매번 확인 중).

`createImageData`/`putImageData`를 아예 제거한 환경에서도 팝업이 정상
렌더링되고(`fillRect` 798회 호출 확인), 드래그로 색을 고르는 것까지
정상 동작함을 검증했습니다.

## v2.1 변경사항 — 단축키를 F11/F12로 변경 (Photoshop 기본 단축키와 충돌 방지)

Ctrl 등 조합키는 Photoshop 자체 단축키와 너무 많이 겹쳐서, 기본값을
**F11(팝업 표시) / F12(스포이드↔브러시 토글)** 로 바꿨습니다.

- **F11**: 누르고 있는 동안 커서 위치에 컬러 팝업 (기존과 동일한 동작)
- **F12**: 하나의 키로 토글
  - 1번째 누름 → Photoshop이 스포이드 도구로 전환 (`activateEyedropper`)
  - 그 상태에서 2번째 누름 → 브러시 도구로 복귀 (`activateBrush`,
    Photoshop 액션 매니저 참조명 `paintbrushTool` 사용)
  - 3번째 누름 → 다시 스포이드로... (계속 토글)
- 팝업 안의 스포이드 아이콘을 눌러도 이 토글 상태와 동기화됩니다 (아이콘으로
  스포이드를 켰다면, F12를 눌렀을 때 "이미 스포이드 상태"로 인식해서
  브러시로 돌아가지, 다시 스포이드를 켜려 하지 않습니다).

Node.js로 F12를 3연속 눌렀을 때 정확히
`activateEyedropper → activateBrush → activateEyedropper` 순서로 토글되는지
직접 검증했습니다 (실제 uiohook 키 감지 자체는 이 환경에서 검증 불가 —
아래 "검증 못한 것" 참고).

## v2.0 변경사항 — 팝업 UI를 TourBox 스크린샷 구조로 교체

기존 원형 타일 링 팝업을 없애고, Photoshop 플러그인 패널(v1.5.0)과 완전히
동일한 **비정형 블롭 필드 + 명도 슬라이더 + 상단 스포이드 아이콘 + 하단
2단 스와치** 구조로 바꿨습니다. Ctrl을 누르고 있으면 이 전체 UI가 커서
근처에 뜹니다.

- **드래그로 색 선택**: 필드 안에서 드래그하면 색상/채도가 동시에 바뀌고,
  손을 떼는 순간(pointerup) 그 색이 확정되어 Photoshop 전경색으로 적용되고
  팝업이 닫힙니다.
- **명도 슬라이더**: 드래그하면 필드가 그 밝기 기준으로 다시 그려집니다.
- **스포이드 아이콘**: 클릭하면 Photoshop이 스포이드 도구로 전환되고
  팝업이 닫힙니다 (이후 캔버스 클릭으로 색 추출).
- **팝업 위치**: 커서 오른쪽 아래에 뜨되, 화면 가장자리를 벗어나면 반대쪽에
  붙도록 clamp 처리했습니다.
- `colorMath.js`를 렌더러(팝업 창)에서 직접 쓰기 위해, `preload.js`에서
  순수 함수들(`labFieldPixel`, `abToPolar` 등)을 `contextBridge`로 노출하는
  방식으로 바꿨습니다.

**버그 수정**: 이 오버레이 앱 폴더의 `colorMath.js`가 Photoshop 플러그인
쪽에서 `labFieldPixel`/`lumaFieldPixel` 등을 추가한 이후로 동기화가 안 돼
있던 걸 발견해서(구버전 복사본) 최신 버전으로 다시 복사했습니다. 두
프로젝트가 이 파일을 각자 복사해서 쓰는 구조라, 앞으로 `colorMath.js`를
고칠 때는 항상 양쪽에 다시 복사해야 합니다.

### 3. 실제 사용 (핵심 워크플로우)

1. Photoshop에서 브러시 도구 선택, 캔버스에 그림을 그리는 중이라고 가정
2. **F11 키를 누르고 있는다** → 지금 마우스/펜 커서 위치에 색상 팝업이 뜸
3. 원하는 색 타일을 **클릭** → 그 즉시 전경색이 바뀌고 팝업이 닫힘
4. Ctrl을 떼기만 하고 클릭을 안 하면 → 아무 변화 없이 팝업만 닫힘
5. 계속 그림을 그림 (마우스를 팝업 쪽으로 옮기지 않고, 원래 그리던 자리에서
   바로 처리됨)

추가로, 캔버스 위에서 직접 색을 추출하고 싶으면: 설정 패널에서
"스포이드 모드로 전환" 키를 지정해두면, 그 키를 눌렀을 때 Photoshop이
스포이드 도구로 바뀌고, 클릭해서 뽑은 색 기준으로 Photoshop 패널 쪽의
색역 필드가 자동 갱신됩니다.

### 4. 단축키 바꾸기 (설정 패널)

트레이 아이콘 우클릭 → **"설정 (단축키 변경)..."** 클릭:

- **팔레트 팝업 표시**: 기본값 `F11`. "키 입력으로 변경" 누르고 원하는 키를
  누르면 바로 그 키로 바뀝니다 (Esc로 취소).
- **스포이드 모드로 전환**: 기본값 `F12` (스포이드↔브러시 토글). 마찬가지로
  키 입력으로 지정 가능하고, ✕ 버튼으로 다시 비활성화할 수 있습니다.
- **클릭 추적 모드 전환**: 기본값 `F9`. 켜면 좌클릭을 누르고 있는 동안에만
  팝업이 커서를 따라다니고(F11은 무시됨), 다시 누르면 원래의 F11
  hold-to-show 방식으로 돌아갑니다.
- **색 스캔**: 기본값 `F10`. 누르고 있는 동안만 커서 아래 화면 색을
  실시간으로 팔레트에 반영하고, 떼는 순간 그 색으로 고정됩니다.
- **스캔된 색을 브러시로 적용**: 기본값 `F8`. 지금 잡혀있는 색을 실제
  Photoshop 전경색으로 확정합니다.
- 변경 후 **저장** 버튼을 눌러야 반영됩니다 (`userData` 폴더의 JSON 파일에
  저장되어 다음 실행에도 유지됨).

지금은 지원 키 목록이 제한적입니다: `Ctrl`, `Alt`, `Shift`, `Space`,
`F9`~`F15`(펑션 확장키, 매크로 키보드에 흔함). 더 다양한 키(예: 마우스
사이드 버튼, 숫자패드 등)를 지원하려면 `main.js`의 `keyNameToUiohookCode`
매핑 테이블만 넓히면 되니 필요하면 말씀해주세요.

## 아키텍처

```
[uiohook-napi로 Ctrl keydown 감지] → [커서 위치에 팝업 표시, 클릭 대기]
       ↓ (타일 클릭 시)
[popup-tile-picked IPC] → [WebSocket으로 UXP 플러그인에 setColor 전송]
                                    ↓
                    UXP 플러그인이 실제 batchPlay로 전경색 적용
```

- `uiohook-napi`(OS 레벨 키보드 후킹)로 진짜 "누르고 있는 동안"을 감지합니다.
  Electron 기본 `globalShortcut`은 keyup 이벤트가 없어서 이 방식이 불가능했던
  것을 해결한 것입니다.
- 팝업이 보일 때만 클릭을 받도록 `setIgnoreMouseEvents`를 동적으로 토글합니다
  (평소엔 완전 클릭-스루라 Photoshop 캔버스 조작을 방해하지 않음).
- 설정은 `config.js`가 `app.getPath('userData')`에 JSON으로 저장/로드합니다.

## 검증한 것 / 못한 것

**Node.js로 직접 실행해서 검증**: 설정 저장/로드 로직, WebSocket 프로토콜
(`setColor`/`activateEyedropper` 왕복), 설정 창의 키 녹화 UI 로직(jsdom).

**이 환경(디스플레이 없는 리눅스 샌드박스)에서 검증 못한 것**:
- `uiohook-napi`가 실제로 설치/빌드되고 Ctrl keydown/keyup을 정확히
  잡아내는지 (네이티브 모듈이라 플랫폼별 prebuilt 바이너리 다운로드 필요 —
  `npm install` 시 네트워크로 받아옵니다)
- macOS 권한 팝업이 뜨고, 허용 후 정상 동작하는지
- 팝업이 실제로 Photoshop 캔버스 위, 커서 바로 옆에 정확히 뜨는지
- 트레이 아이콘이 각 OS에서 정상적으로 보이는지
- 설정 창에서 실제 물리 키보드로 키를 눌렀을 때 정확한 키 이름이 잡히는지

실제로 `npm start` 해보시고 위 항목 중 안 되는 게 있으면 알려주세요.
